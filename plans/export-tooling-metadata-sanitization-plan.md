# Export Tooling Metadata Sanitization Plan

Date: 2026-04-09

## Goal

Remove export metadata that exposes private or incidental implementation details while preserving:

- rendering behavior
- animation playback
- user-selected export settings
- intentional Supericons branding
- any code or attributes required for the export to work

This plan is narrower than the earlier premium cleanup. The rule here is not "remove all comments." The rule is "remove only comments or metadata that reveal tooling, generation method, source pipeline, or internal/private implementation details that users do not need."

## Minimal Compliance Baseline

We should pair the metadata cleanup with a minimal compliance posture so we do not confuse "remove noisy attribution comments" with "remove all upstream notice obligations."

Minimal compliance for this plan means:

- do not keep source/tooling attribution comments inside exported SVG, CSS, HTML, Base64, or framework snippets just to satisfy licensing
- keep any required third-party notices in one central compliance surface instead of scattering them across user-facing exports
- preserve intentional Supericons branding where product wants it
- treat brand-logo libraries separately from ordinary icon libraries when needed

Recommended minimal compliance surface:

- add a repo-level `THIRD_PARTY_NOTICES.md` or `LICENSES.md`
- list each bundled icon source with:
  - library name
  - license family
  - upstream project link
  - short note if special handling applies
- if Supericons distributes packaged builds outside the repo, ensure that same notice file is included in the distributable or linked from it

Working compliance rule for this implementation:

- MIT / ISC / Apache-style libraries do not require visible attribution inside every exported asset, so export sanitization can safely remove tooling/source comments from customer payloads
- Simple Icons and other brand-logo sources should be called out in the central notice file with an extra note that brand/trademark guidelines may still apply
- internal generation comments like `Generated by ...`, `Using ...`, `Source: ...`, and pipeline notes are not a substitute for proper license notices and should still be stripped from public-facing payloads

## Decision Rule

Before excluding any text, run it through this Socratic filter:

1. Does this text affect rendering, animation, sizing, interactivity, or framework integration?
2. Is this text intentionally public product branding or user-helpful documentation?
3. Does this text reveal an external tool, internal method, source pipeline, authoring notes, or implementation provenance that is not needed by the customer?
4. If removed, would the exported file still behave identically?

Decision guidance:

- If the answer is `yes` to 3 and `no` to 1 and 2, strip it.
- If the answer is `yes` to 1, preserve it.
- If the answer is `yes` to 2, preserve it unless product explicitly wants minimal output.
- If uncertain, prefer preserving structure and only stripping non-executable comment metadata.

Examples:

- Keep: `/* Supericons Motion Lab */`
- Strip: `<!-- Generated by @neplex/vectorizer (Using visioncortex VTracer) -->`
- Strip: source/tooling comments such as `Generated by build-...`, `Using ...`, `Source: ...`
- Usually keep: classes, ids, selectors, keyframe names, path classes

## Why This Plan Exists

We confirmed at least one customer-facing leak in converter exports:

- `<!-- Generated by @neplex/vectorizer (Using visioncortex VTracer) -->`

`@neplex/vectorizer` is a public dependency, not a private Supericons package, but exposing it in exported files still reveals implementation/tooling details that are not customer value.

We also need to protect against the same class of leak across other outbound payloads so this does not reappear through a different export route later.

### Confirmed leak source: Converter SVG output preserves upstream XML comments

- `normalizeSvgOutput(...)` in [store.js](/d:/Personal/Business/Curly%20Mole%20Labs/Experiments/Apps/DailySprint/supericons/store.js#L11258) rewrites root sizing attributes but does not strip XML comments.

- Result: tool-generated XML comments survive into copied/downloaded converter SVG payloads.

### Adjacent risk: Free icon exports have no outbound SVG metadata sanitizer

- `applyExportCustomization(...)` in [main.js](/d:/Personal/Business/Curly%20Mole%20Labs/Experiments/Apps/DailySprint/supericons/main.js#L161) customizes SVGs but does not sanitize XML comments or metadata comments.
- Framework export wrappers in [main.js](/d:/Personal/Business/Curly%20Mole%20Labs/Experiments/Apps/DailySprint/supericons/main.js#L2234) and [main.js](/d:/Personal/Business/Curly%20Mole%20Labs/Experiments/Apps/DailySprint/supericons/main.js#L2242) do not add tooling comments themselves, but they will faithfully ship whatever is already inside the SVG payload.
- That means future source SVGs containing generator comments or private provenance notes would leak across:
  - copy SVG
  - download SVG
  - base64
  - React
  - Vue
  - Svelte
  - HTML
  - batch ZIP exports

### Broader pack risk: public collection assets bypass export sanitization entirely

Even after export flows are fixed, public pack assets will still leak if they keep authored comments in raw browser-shipped files.

That affects:

- collection CSS files in `public/packs/**`
- bundle payloads like `public/packs/**/bundle.json`
- raw custom SVG assets in `public/packs/**`

So the plan needs two lanes:

- export-payload sanitization
- public-asset sanitization

### Motion Lab status: not a confirmed private-method leak today, but it needs a rubric-based review

- `generateFullCSS(...)` in [store.js](/d:/Personal/Business/Curly%20Mole%20Labs/Experiments/Apps/DailySprint/supericons/store.js#L5792) currently emits comments including:
  - `/* Supericons Motion Lab */`
  - `/* Animation: ... | Trigger: ... | Duration: ... */`
  - `/* Static overrides */`
  - `/* Root transform overrides */`
- `buildMotionLabExternalCss(...)` in [store.js](/d:/Personal/Business/Curly%20Mole%20Labs/Experiments/Apps/DailySprint/supericons/store.js#L5881) also appends a usage note comment.
- `showExportModal(...)` in [store.js](/d:/Personal/Business/Curly%20Mole%20Labs/Experiments/Apps/DailySprint/supericons/store.js#L7639) distributes that CSS into copy/download/export SVG flows.

Assessment under the new rule:

- `/* Supericons Motion Lab */` is acceptable and should remain.
- The animation state comments and usage-note comments are not obviously private tooling leaks, so they should not be stripped by default in this plan.
- However, Motion Lab should still adopt the same sanitization framework so that future internal/tool-specific comments do not leak if they are introduced later.

### Out of scope for this fix

- Placeholder comments in modal empty states such as `<!-- Load an SVG first -->` and locked-state placeholder strings are not part of successful export payloads.
- Premium export sanitization was already addressed separately in [premium-export-metadata-sanitization-plan.md](/d:/Personal/Business/Curly%20Mole%20Labs/Experiments/Apps/DailySprint/supericons/plans/premium-export-metadata-sanitization-plan.md).

## Constraints

- Do not break existing export behavior or payload validity.
- Do not strip classes, ids, selectors, or style rules unless they are proven unnecessary.
- Do not remove brand-safe public comments that product wants to keep.
- Do not accidentally remove or bypass the minimal central notice surface we need for third-party compliance.
- Do not alter icon geometry, colors, stroke widths, or animation behavior.
- Do not break entitlement, gating, or protection measures.
- Prefer central sanitization at payload boundaries rather than format-by-format patching.

## Implementation Strategy

### Phase 0: Establish minimal compliance without polluting exports

Before or alongside sanitization, define a small central notice surface so legal hygiene does not depend on noisy comments embedded in customer payloads.

Recommended work:

- add a root-level `THIRD_PARTY_NOTICES.md` or equivalent
- include the icon libraries currently bundled by Supericons
- record license family and upstream link for each
- add a special note for brand-logo sources like Simple Icons that trademarks and brand guidelines may still apply

Important:

- this phase should not inject comments back into exported files
- this phase should not add visible attribution UI unless product explicitly wants that later
- this is a central compliance artifact, not a per-export annotation system

### Phase 1: Add a shared outbound metadata classifier

Create small, conservative helpers dedicated to comment sanitization.

Recommended helpers:

- `stripXmlComments(svgText, shouldRemoveComment)`
- `stripCssComments(cssText, shouldRemoveComment)`
- `shouldStripExportMetadataComment(commentText, context)`

`shouldStripExportMetadataComment(...)` should implement the Socratic filter as code.

Initial strip heuristics should target comments containing patterns like:

- `generated by`
- `using `
- `source:`
- `built with`
- `curated from`
- `vtracer`
- `vectorizer`
- `visioncortex`
- `authoring note`
- `internal`

Initial preserve heuristics should allow:

- `supericons`
- short product-facing usage guidance when intentionally public
- neutral section labels that do not expose private methods

Important:

- do not regex-delete arbitrary comments globally without classification
- do not touch executable CSS or SVG markup outside comment nodes

### Phase 1B: Add a repo-wide public-surface audit inventory

Create and maintain a simple inventory of public-facing leak sites so we can track them by category:

- export payload leaks
- browser-shipped asset leaks
- low-risk descriptive comments

This can be a Markdown audit note or be folded into this plan during implementation, but the key is to distinguish:

- comments that expose tools or methods and must go
- comments that are merely verbose and can be deferred

### Phase 2: Fix converter exports first

Converter is the confirmed leak and should be the first remediation target.

Update the converter artifact builders so the SVG is sanitized before the final blob/string is returned:

- `buildConverterTraceArtifact(...)`
- `buildConverterServiceTraceArtifact(...)`
- any other converter path that turns traced SVG into copied/downloaded output

Apply sanitization after structural SVG cleanup but before blob creation so every downstream consumer receives the same sanitized payload.

This covers:

- copied converter SVG
- downloaded converter SVG
- any later converter-derived SVG payload reuse

### Phase 2B: Sanitize browser-shipped public assets with classified metadata

Apply the same classifier to the raw public assets that ship directly to the browser.

Initial high-priority targets:

- `public/packs/status-feedback/status-feedback.css`
- `public/packs/status-feedback/bundle.json`
- `public/packs/media-playback/media-playback.css`
- `public/packs/navigation-menus/navigation-menu.css`

For these files:

- strip source/tooling/authoring comments that expose generation method or external source provenance
- preserve executable CSS and JSON structure
- preserve any comments explicitly approved as public branding

Important:

- because `bundle.json` stores CSS as a JSON string, sanitization must preserve valid JSON escaping
- do not manually edit derived pack artifacts in a way that drifts from their source generation path if a safe regeneration route exists

### Phase 3: Add a defensive shared sanitizer to free-icon outbound SVG paths

Free icon exports are not currently leaking tool/source comments from the code we audited, but they lack a generic guardrail.

Add a lightweight outbound SVG sanitization step to the shared free export payload path, ideally where `resolveExportSvg(...)` or an adjacent shared helper returns the final exported SVG string.

That single change should protect:

- single-icon copy SVG
- single-icon download SVG
- base64 export
- React export
- Vue export
- Svelte export
- HTML export
- multi-select copy SVG
- ZIP download SVG batches

This should only remove comments classified as private/tooling metadata. It should not strip harmless structural classes or alter SVG contents otherwise.

### Phase 4: Apply the same classifier to Motion Lab, but preserve approved public comments

Motion Lab should adopt the shared comment-classification utilities even if the resulting behavior today is "preserve current public-safe comments."

That gives us:

- future-proof protection if a tool/source/internal comment enters Motion Lab CSS generation later
- consistency across all export systems

Policy for this phase:

- keep `/* Supericons Motion Lab */`
- keep other Motion Lab comments unless they match private/tooling leak rules
- do not refactor user-facing CSS comments just for minimalism in this pass

### Phase 4B: Defer low-risk descriptive SVG comments unless product wants a broader hygiene pass

Examples include raw custom SVG comments like:

- `<!-- Frame -->`
- `<!-- Plus sign -->`
- `<!-- Handle -->`

These do not currently expose tooling or private methods, so they should not be stripped as part of the classified-metadata fix unless product explicitly chooses a second cleanup pass for public-source neatness.

### Phase 5: Add regression coverage for all public-facing payload families

Add targeted verification around the final payloads, not internal helpers alone.

We want snapshot-like checks or deterministic string assertions for:

- converter SVG export
- free icon SVG export
- free icon base64 export
- free icon framework export snippets
- Motion Lab CSS export
- Motion Lab self-contained SVG export
- public collection CSS assets
- public pack bundle payloads

Focus assertions on absence of prohibited comment patterns rather than exact full-string snapshots where possible.

## Risks And Mitigations

### Risk: Over-stripping comments that product intentionally wants to keep

Mitigation:

- use classifier-based removal, not blanket comment deletion
- explicitly preserve approved public comments like `Supericons Motion Lab`

### Risk: Stripping content that affects rendering

Mitigation:

- only remove comment nodes, never selectors, declarations, classes, ids, or attributes
- sanitize after structural rewriting/customization is complete

### Risk: Multiple export systems drift apart

Mitigation:

- centralize the classifier helpers
- reuse the same decision rule in converter, free exports, and Motion Lab

### Risk: Public pack files get manually cleaned but regenerated later with the same leaks

Mitigation:

- identify whether each file is source-authored or generated
- patch the generator path when one exists
- use verification checks to catch reintroduction

## Definition Of Done

- A central minimal-compliance notice surface exists for bundled third-party icon sources.
- Converter exports no longer leak external/internal tool attribution comments.
- Free icon outbound exports are protected against the same class of metadata leak.
- Motion Lab keeps approved public branding comments but is guarded against future private tooling leaks.
- Public browser-shipped pack assets no longer expose classified tooling/source/authoring comments.
- No rendering, animation, color, sizing, or framework export regressions are introduced.
- Existing protection measures remain intact.
