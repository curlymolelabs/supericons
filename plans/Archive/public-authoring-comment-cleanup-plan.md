# Public Authoring Comment Cleanup Plan

Date: 2026-04-09

## Goal

Remove the remaining public-facing comment and metadata leaks that expose internal authoring methods or process notes, while preserving:

- rendering behavior
- animation behavior
- export behavior
- runtime-required configuration
- intentional Supericons branding
- minimal open-source compliance through the central notice file

This plan is intentionally narrower than the earlier metadata-sanitization passes. The target here is not "remove comments in general." The target is "remove public-facing text that reveals how we authored or reasoned about the assets."

## Agreed Rule

### Keep

- short public collection labels such as:
  - `E-Commerce Collection: CSS-only hover animations`
  - `Supericons Motion Lab`
- code-level identifiers that are required or harmless:
  - classes
  - ids
  - selectors
  - keyframe names
  - path class names such as `sa-finger`
- runtime-required manifest/config fields until they are safely refactored away

### Remove

- internal method or process comments such as:
  - `Socratic design: 1. What real-world thing? 2. What motion? 3. Which elements? 4. Same at rest?`
  - `Animation story: Main star pops in with elastic bounce...`
  - `Each animation designed via Socratic method: ...`
  - `Every keyframe is purpose-built. No generic reuse where stories differ.`
  - `Concept: ...`
  - `Story: ...`
- tooling or source-pipeline attribution that is not required for compliance:
  - `Generated by ...`
  - `Using ...`
  - `Source: ...`
  - vendor/toolchain references such as `@neplex/vectorizer`, `visioncortex`, `VTracer`

## Socratic Filter For Safe Removal

Before removing any text, apply these questions:

1. Does this text change rendering, playback, export behavior, or runtime data loading?
2. Is this text an intentional public-facing label or brand marker?
3. Does this text reveal internal authoring method, motion rationale, process notes, tooling provenance, or generation pipeline details?
4. If removed, will the file still behave identically?

Decision rule:

- If `1 = no`, `2 = no`, `3 = yes`, and `4 = yes`, remove it.
- If `1 = yes`, keep it.
- If `2 = yes`, keep it unless product explicitly wants a leaner public surface.

## Compliance Position

The manifest fields:

- `provider`
- `repo`
- `baseUrl`

are not required as public fields for open-source license compliance.

Minimal compliance should remain centralized in:

- [THIRD_PARTY_NOTICES.md](/d:/Personal/Business/Curly%20Mole%20Labs/Experiments/Apps/DailySprint/supericons/THIRD_PARTY_NOTICES.md)

That means we can safely remove process/tooling/method comments without weakening open-source notice hygiene.

## Implementation Strategy

### Phase 1: Narrow the sanitizer classification

Update the shared comment classifier in:

- [public-metadata-sanitizer.js](/d:/Personal/Business/Curly%20Mole%20Labs/Experiments/Apps/DailySprint/supericons/lib/public-metadata-sanitizer.js)

Add strip patterns for internal authoring-method text, including phrases like:

- `Socratic design`
- `Socratic method`
- `Animation story`
- `Concept:`
- `Story:`
- `Every keyframe is purpose-built`

Preserve patterns for short public branding/section labels, including:

- collection title comments
- `Supericons Motion Lab`

Important:

- do not broaden the classifier so much that it removes harmless structural comments from SVG markup
- do not strip executable CSS or selectors

### Phase 2: Re-sanitize browser-shipped pack CSS

Run the updated sanitizer against the public pack CSS sources so the cleaned files under `public/packs/**` no longer ship method/process text.

Primary targets:

- ecommerce
- social-communication
- ai-agentic

Then scan all pack CSS files for any remaining method/process phrases.

### Phase 3: Rebuild bundle payloads

Regenerate any derived bundle payloads so the cleaned CSS is reflected in:

- `public/packs/**/bundle.json`

This ensures the leak is removed both from raw CSS assets and JSON payloads consumed by the browser.

### Phase 4: Review runtime manifest fields safely

Do a small dependency check for:

- `provider`
- `repo`

If no runtime code uses them, remove them from:

- [material-export.js](/d:/Personal/Business/Curly%20Mole%20Labs/Experiments/Apps/DailySprint/supericons/material-export.js)
- [material-export-manifest.json](/d:/Personal/Business/Curly%20Mole%20Labs/Experiments/Apps/DailySprint/supericons/public/material-export-manifest.json)

Leave these in place for now:

- `baseUrl`
- `functionBaseUrl`

If later we want to hide those too, that should be a separate refactor to move fetch routing behind internal endpoints rather than a blind metadata deletion.

## Risks And Guardrails

- Main risk: over-sanitizing comments and accidentally removing brand-safe section headers that product wants to keep.
- Secondary risk: deleting manifest fields that still have hidden runtime consumers.
- Guardrail: treat `provider` and `repo` as optional-removal items only after grep-level dependency confirmation.
- Guardrail: do not touch `baseUrl` or `functionBaseUrl` in this pass.
- Guardrail: preserve `THIRD_PARTY_NOTICES.md` as the compliance surface instead of trying to satisfy compliance through public runtime comments.

## Definition Of Done

This plan is complete when:

- no public browser-shipped CSS or bundle payload includes internal method/process commentary
- public-facing collection labels that product wants are still present
- material export flow still works
- open-source compliance remains centralized in `THIRD_PARTY_NOTICES.md`
- no runtime-required manifest fields were removed accidentally
