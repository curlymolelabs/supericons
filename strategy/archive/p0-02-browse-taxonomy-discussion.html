P0.02 Browse Taxonomy:
Socratic Design Analysis

The database layer is live. The taxonomy seed is applied. The evidence pipeline is collecting data. The only question is: what is the correct UI expression of the job-shaped taxonomy? This document synthesizes the full discussion using Socratic prompting and IDEO design thinking to arrive at the optimal decision.

April 16, 2026 -- Post P0.01/P0.02 Implementation Audit
01
The Triggering Question
"Did we want to add the Jobs menu to the sidebar?"

The builder added a "Jobs" section to the sidebar with three categories: AI & Agents (50), Navigation & Wayfinding (50), Status & Feedback (50). This surfaced a fundamental product question: what is the correct UI expression of the P0.02 taxonomy?

The builder's own assessment, after discussion: "The Jobs sidebar is not the right final UI." Two concerns were conflated: GitHub distribution packs (external repos) and taxonomy as an internal classification layer (search, ranking, filtering, telemetry). These are related but not the same UI surface.

02
What the Master Plan Actually Says

From supericons-master-action-plan.html, Section P0.02:

"Replace the current library-centric browse categories (Buildings, Arrows, Technology...) with a product-job taxonomy."

Done criteria:

"Browse page shows 14 job categories. AI & Agents category is fully populated. At least the 150 most common icons have primary categories assigned."
⚠
Critical observation: The phrase "Buildings, Arrows, Technology..." refers to category patterns used by other icon libraries (Heroicons, Phosphor, Iconify). Supericons has never had these subcategories. The current sidebar shows only library names with counts. The taxonomy is a net addition, not a replacement of something that existed.
03
Socratic Analysis: Five Questions
Q1: "What is best practice for this?"
Faceted search. Every major product catalogue (Amazon, Shopify, Figma Community, Iconify) uses multi-dimensional faceted filtering. None of them put categories as sidebar navigation items parallel to brands/libraries. Categories are always a filtering axis, not a navigation axis.
Q2: "What would a senior engineer do?"
Separate data layer from UI layer. The taxonomy (icon_metadata, JOB_CATEGORY_DEFINITIONS, telemetry tagging) is correctly built and should not change. Only the presentation needs to change. The existing search engine already has 5-layer expansion logic. The path of least resistance is extending synonyms.json, not building new UI.
Q3: "What is the safest reversible option?"
Enhance synonyms first. Add AI-domain terms to synonyms.json (zero UI change, zero risk, immediately valuable). Then decide on filter UI after testing the improved search results.
Q4: "Does the codebase already have a pattern for this?"
Yes. synonyms.json (285 groups, 1500+ terms) powers a proven 5-layer search: direct match, synonym expansion, reverse lookup, prefix match, fuzzy typo tolerance. The search results are already tiered (direct first, "Related" below). Extending it requires no architecture change.
Q5: "What would break if I am wrong?"
Low risk either way. If we ship the Jobs sidebar: users see confused IA where "AI & Agents" sits alongside "Lucide" as equivalent choices, creating the wrong mental model. If we ship enhanced search only: worst case is users find more relevant results. Low risk.
04
IDEO Design Thinking: Three Lenses
LensQuestionAnswer
Desirability What do users want? Two intents: "quota" (known need, semantic search) and "show me AI icons" (exploration, browse filter). Jobs sidebar partially serves exploration but totally fails known-need search.
Feasibility What is technically possible? Search engine already has multi-layer expansion. Adding terms to synonyms.json is editorial work, not engineering. JOB_CATEGORY_DEFINITIONS can power filter chips with minimal code.
Viability What makes business sense? The competitive moat is: "When you type 'quota' on Supericons, you find the right icon. On Iconify, you find nothing." The differentiation must be expressed as smarter search, not sidebar clutter.

10
Decision Points for Builder
D1: Synonym Enhancement Scope
Start with Kit 01 amber aliases only (31 icons worth of terms). All documented explicitly in the reference guide. The remaining 100 icons in the taxonomy seed do not have editorial semantic aliases yet.
D2: Filter Chip Data Source
Use JOB_CATEGORY_DEFINITIONS (client-side). Already loaded at startup, already counted in rebuildJobCategoryCounts(), requires zero API calls. The database is for telemetry and MCP, not for the browse UI.
D3: Filter Chip Behavior
Intersection (AND). "Lucide + AI & Agents" = only Lucide icons tagged AI. This is the e-commerce standard. "Nike + Shoes" shows Nike shoes, not all Nike products plus all shoes.
11
What NOT to Do
1
Do not tag all 20K icons manually first. The 150 seeded icons and the existing synonym corpus cover the highest-traffic cases. Expand editorially over time, driven by search analytics showing zero-result queries.
2
Do not put filters inside the search bar as a dropdown. Search-bar filter dropdowns have poor mobile UX and add interaction complexity. Keep the search bar as a text input. Keep filters as a separate visual row.
3
Do not add more sidebar sections. The sidebar serves library navigation. Adding another dimension there creates parallel-axis confusion. The filter chip row is the correct surface for the second dimension.
4
Do not build a faceted search backend. The current client-side filter+search architecture works at 20K icons. Server-side faceted search is overengineering for this scale.
12
Verdict: Browse UI
✅
The P0.02 data layer is correct and complete. The evidence pipeline is live. The taxonomy seed is applied. The only error is the UI surface. The Jobs sidebar should be replaced with a filter chip row above the grid.

The highest-impact immediate action is not UI work. It is adding AI-domain synonym terms to the existing synonyms.json so that search queries like "quota", "rag", and "observability" return results today. Zero UI change, immediate improvement.
13
Tag All 20K Icons vs. Enhance Synonyms: Socratic Conclusion

Searching "compute" returns 4 results: lucide:cpu (correct) plus computer_line, computer_camera_line, computer_camera_off_line (all wrong -- physical device icons, not computing concepts). This exposes a precision limitation of synonyms-only search. Does the solution require tagging every icon?

Q1: "What is the actual problem being solved?"
Two distinct problems exist, often conflated. They need different solutions.
ProblemSymptomRoot CauseSolution
Gap problem"quota" = 0 resultsTerm missing from synonyms entirelyEnhance synonyms.json
Noise problem"compute" = camera icons"computer" contains substring "compute"Per-icon tags for curated 150
Q2: "What is the cost of tagging all 20K icons?"
Manual editorial tagging at 30 seconds per icon, 5 tags each = 167 hours of human time. This is a multi-month sustained operation, not a sprint task. More importantly: before traffic exists, you are guessing what users need instead of learning it from data.
Q3: "What does 'tagging' actually mean architecturally?"
Adding a tags[] array to icon data is one line of code in the search engine. The architecture question is not whether to have tags -- it is how to populate them efficiently:
MethodCoverageEffortPrecision
Manual (all 20K)Complete167+ hoursHigh
Editorial (150 curated)Known gaps only~8 hoursHigh
Behavioral (P0.01 pipeline)Grows with trafficZeroEmerges from real usage
LLM tagging pipelineNear-complete1 day + computeMedium (needs QA)
Q4: "What is the right sequence?"
The icon_evidence pipeline (P0.01, already live) is the engine that discovers which icons need tags next. Traffic tells you where gaps are. You do not need to front-load all tagging before the first user arrives.

Phase sequence:

P0 (now)
Synonyms enhanced + 150 curated icons tagged = closes all known gaps immediately
P1-P2
Traffic flows. Evidence pipeline collects real search behaviors. Zero-result queries surface automatically.
P3+
icon_evidence surfaces the next 500+ icons needing tags, in priority order by actual user impact. LLM pipeline if scale warrants it.
⚠
The noise fix for "compute" returning camera icons: Add precise tags to the 150 curated icons. lucide:cpu gets tags:["inference","compute","quota"]. computer_line gets tags:["device","desktop","laptop"]. The search engine ranks tag matches above substring matches, so lucide:cpu rises to Tier 1 for "compute" and the camera icons disappear. ~8 hours editorial work. Zero new architecture.
✅
Final answer: The tag-all-20K question is not "yes or no" -- it is "not yet, and maybe never manually." The behavioral pipeline discovers which icons need tags next, in priority order. Ship synonyms + 150 icon tags now. Let traffic teach you the rest.
