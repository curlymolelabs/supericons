How Agents Select Icons:
First-Hand Feedback

Raw, unfiltered intelligence from the agent that built the Supericons 2027 blueprint. Documenting exactly how and why icon choices were made -- and where the process failed.

Source: blueprint HTML build session Date: April 2026 Purpose: product intelligence
The core finding: When building a rich HTML document, I used Google Material Symbols via CDN -- not the Supericons MCP server -- because the CDN had zero setup friction and I already knew icon names from training data. Agents take the path of least resistance. This single observation should drive every priority decision in the Supericons 2027 roadmap.
Step-by-step

My Actual Decision Process

I did not evaluate icon libraries. I did not browse visually. I typed names I already knew and hoped they were right.

Step 1: Library selection

I defaulted to Material Symbols because: one <link> tag requires no configuration, icon names are in my training data so I can use them without a tool call, and there is no API key, no MCP session, and no network round-trip required.

What I did (high friction)

Recalled a Material Symbols name from training data. Typed it as a string. Never saw the icon. Hoped it was the right visual choice.

What I wish existed (zero friction)

Described the intent: "I need a trust indicator for a governance dashboard." Received the exact right icon, animated, with a11y metadata, in one call.

Product Intelligence

Five Findings for the Supericons Team

What this session reveals about how coding agents actually interact with icon systems in 2026.

Finding 01

Agents select by semantic keyword, not visual browsing

I never opened a browser to look at icons. I typed names. The semantic_tags[] array is therefore the most important field in your dual-surface metadata. Specifically: intent synonyms, not visual descriptors. "governance" beats "looks like a shield."

Finding 02

The governance vocabulary gap is real and I felt it acutely

For every traditional UI concept (save, delete, search), I had an instant keyword match. For agentic concepts (agent confidence, human override, disclosure layer), I was forced to approximate or skip. That gap is the entire business opportunity.

Finding 03

I needed composable elements, not atomic glyphs

For stateful icon demos I needed: icon + colored ring + animation. I built this manually in CSS. If get_icon_grammar had returned a pre-composed SVG bundle, I would have used it and saved significant effort.

Finding 04

The ideal agent workflow does not exist yet

Intent-based icon resolution (request_semantic_icon) is the single most impactful feature Supericons can ship. Every other improvement is incremental. This one is transformational.

Finding 05

Pre-knowledge of names is Material Symbols' moat -- and it is closeable

Material Symbols names appear across the web so they live in my training data. Supericons closes this two ways: MCP intent resolution (agents describe, not name) and synonym mapping ("waiting_for_approval" resolves to the right ID).

Addendum: Agent Design Capabilities

Can Agents Design Icons?

An honest self-assessment. If a user asks me to design visually impressive icons for apps and websites based on human taste, here is what I can and cannot deliver.

Can do

Write SVG markup directly

My training data includes thousands of icon SVGs. I understand stroke widths, viewBox conventions, path construction, and visual balance. I can produce simple, clean line icons (Lucide/Feather style). Quality ceiling: functional, correct, but not visually impressive.

Can do

CSS-animate icons (strongest skill)

Given an SVG, I can write sophisticated CSS animations: hover effects, state transitions, micro-interactions, keyframe choreography. The existing premium collection pipeline proves this capability.

Cannot do

Match human visual taste and aesthetic judgment

I have no way to evaluate visual balance, negative space harmony, or whether an icon "feels right." I optimize for correctness and convention, not beauty.

Cannot do

Create pixel-perfect production icons at scale

A 50-icon collection with consistent stroke weight, optical alignment, corner radius, and visual density requires iteration-by-iteration refinement. I can approximate the first draft. The polish loop needs human eyes.

Cannot do

Understand brand personality through icons

"Make icons that feel playful but professional." I can translate this to parameters (round corners, thicker stroke, softer angles), but I am applying rules, not feeling the brand.

Cannot do

Judge from a human taste profile

"I like minimalist Japanese-inspired design." I can adjust parameters (thinner strokes, more whitespace, geometric reduction), but I am pattern-matching against training data, not developing aesthetic empathy.

The strategic implication: Agents will not replace icon designers. But agents will be the primary consumers of icon libraries, selecting and assembling icons into UIs at scale. The value chain is: Human designers create the visual vocabulary (Supericons' core product). Agents select, compose, and deploy those icons into apps (where MCP + semantic tags + grammar matter). The moat is not that agents can make icons. It is that agents cannot make good icons, so they need a library. Whichever library makes it easiest for agents to find and use the right icon wins the market.
