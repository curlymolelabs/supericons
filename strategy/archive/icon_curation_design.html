The Agent-Legibility Problem:
Building an Icon Curation System for the Agentic Era

There are 4,572+ icon repositories on GitHub. Developers have never had more raw icon material. Yet finding the right icon for a specific context remains broken, not because search is bad, but because icons lack the structured semantic metadata that allows either a human or an AI agent to make a confident, reasoned choice. This is a design problem. We solve it with design thinking.

The core question this document answers:
How does an AI agent, which cannot see or visually evaluate an icon, decide which icon from a library of 20,000+ is the most appropriate, trustworthy, and visually-compatible choice for a specific UI context? And how does Supericons build the infrastructure to answer that question confidently, at scale, programmatically?

Research Findings: What Exists vs What Is Missing

✅
What Exists (Solved)
Volume (76K+ icons across all libraries), visual variety (line/fill/duotone/brand), framework wrappers (React, Vue, Svelte packages for every major library), icon aggregators (react-icons already proved this model with 12.5K stars).
❌
What Is Missing (Unsolved)
Intent-based curation (which icons for which product type), semantic metadata schemas for programmatic selection, agent-legible trust signals, design system affinity scoring, industry-specific vocabulary (AI/ML, fintech, health, devtools), and maintained animated icon web libraries.
💀
The Dead Innovation: SVG-Morpheus
In 2015, SVG-Morpheus demonstrated morphing SVG transitions (one icon smoothly transforms into another). It had 2.7K stars and no successor. The concept was profound: icons as animated state machines. This space is still empty in 2026 for web apps.
Opportunity for Supericons
🔄
The Proven Model: Aggregation
React-Icons wraps 30+ icon libraries into one npm package with consistent API. It has 12.5K stars purely because of the aggregation convenience. Supericons already does this with 20K icons. The next level is curated aggregation with intent filtering.
Confirmed Strategy
🧀
The Swiss Cheese Problem
Every major library has vocabulary gaps. Lucide has no icon for "guardrail." Tabler has no icon for "RAG pipeline." FontAwesome has no icon for "model temperature." Every vertical (healthcare, AI/ML, fintech, devtools) has concepts that exist in documentation but not in any open icon library.
Supericons fills this gap
🏷️
The Metadata Desert
Every major icon library provides: name, SVG viewBox, path data. That is all. No semantic aliases, no use-case tags, no design system affinity scores, no "commonly used alongside" data. Agents searching programmatically hit a metadata wall immediately.
The core architectural opportunity
// 02 — DEFINING THE GAP

Three Unsolved Curation Problems

Semantic search is a discovery tool, not a curation system. Discovery finds candidates. Curation makes confident decisions. Supericons currently has excellent discovery. What it needs next is a curation layer that works for humans, for agents, and for AI agents operating without visual capability.

👤
Problem 1: Human Paralysis
A designer knows they need an icon for "AI processing." They search, find 47 results across 6 libraries: loading spinners, brains, lightning bolts, sparkles, gears, chips. All are semantically adjacent. None is definitively "the right one." Without a curated, opinionated recommendation system, they spend 12 minutes scrolling instead of building.
Discovery exists; Decision support does not
🤖
Problem 2: Agent Blindness
An AI coding agent cannot evaluate "does this icon look modern" or "does this icon match the shadcn/ui aesthetic of this codebase." It navigates by text, by schema, by trust signals. A library with rich semantic metadata (aliases, affinity scores, tier ratings) answers questions an agent can actually process. No library currently provides this.
Metadata poverty creates agent failure modes
🌐
Problem 3: Context Vacuum
No icon library knows what you are building. Searching for "home" in any library returns a house icon. But "home" in a fintech app means "dashboard." "Home" in a real estate app means "property." "Home" in an AI agent app means "base state." The icon is the same. The correct choice depends entirely on domain context that zero current libraries capture.
Intent-based curation does not yet exist
// 03 — DESIGN THINKING: EMPATHIZE

Two Users. Radically Different Needs. One System Serves Both.

Classic design thinking begins by understanding not what users do, but what they actually experience. The human and the agent have superficially similar needs (find an icon) but experience the search in fundamentally different ways.

👤
The Human Builder
An indie hacker building a AI observability dashboard. Has a design in mind - dark mode, techy, clean lines. Has been staring at Figma for 3 hours.
What they experience
  • → Search "temperature" and get thermometer icons. Not wrong, but not right either.
  • → Browse 10 different libraries simultaneously in multiple tabs.
  • → Visually compare icon aesthetics but cannot articulate WHY one looks better.
  • ✓ Can perceive quality, style match, and aesthetic coherence instantly.
What they need
Opinionated, curated collections that reduce decision fatigue. Fewer choices with high confidence signal.
🤖
The AI Coding Agent
Claude Code running inside Cursor, tasked with "add icons to the model comparison table in the settings panel for the AI playground app."
What it experiences
  • ✗ Cannot see what any icon looks like visually.
  • ✗ Cannot evaluate whether an icon "matches" the existing design system.
  • → Can read names: "model.svg", "model-selector.svg", "model-card.svg" - but cannot rank their suitability.
  • ✓ Can process structured metadata, trust scores, design affinity tags, and semantic aliases.
What it needs
Structured metadata that substitutes for visual judgment. Schema-driven selection criteria. Trust signals it can reason about. Collections pre-validated for specific contexts.
💡
Key Empathy Insight: Humans need to be stopped from looking (reduce options). Agents need to be given reasons to choose (increase metadata). A curation system that serves both simultaneously is built around the same core: a rich, structured, opinionated semantic layer on top of raw icon data. The human sees it as "collections." The agent sees it as "schema."
// 04 — DESIGN THINKING: DEFINE

The Problem Statement

After empathy comes precise problem definition. A vague problem produces a vague solution. Here is the sharpest possible framing of what Supericons needs to build.

Problem Statement
"Developers and AI agents searching Supericons's 20,000+ icon library need a structured curation system that reduces choice to confident recommendation, because the gap between 'icon exists' and 'icon is the right choice for this specific context, design system, and trust level' cannot be bridged by semantic search alone."
We will know this is solved when: (1) an agent can request "icons for an AI model comparison UI" and receive a pre-curated set with justification metadata, and (2) a human builder lands on a collection page and immediately knows exactly which set is right for their product without scrolling or comparing libraries.

// 05 — DESIGN THINKING: IDEATE

Seven Novel Curation Mechanisms

Seven distinct approaches to solving the curation problem, each targeting a different aspect of the agent-legibility gap. These are not sequential; they are complementary layers of the same system.

🎯
1. Intent-Based Collections
Re-organize the icon library not by source library or visual style, but by what the developer is building. "Icons for an AI monitoring dashboard." "Icons for a fintech transaction UI." "Icons for a developer tools sidebar." Each collection is a pre-curated, opinionated set of 8-25 icons that work together, sourced across any library.
Primary innovation
📋
2. The Icon Manifest
A structured JSON document alongside every icon in Supericons providing: semantic aliases, UI use cases, design system affinity scores, trust tier, co-occurrence partners, contraindication contexts (where NOT to use it). This is the machine-readable intelligence layer that agents navigate instead of visual inspection.
Agent-legibility core
🏅
3. Source Trust Tiers
A transparent, verifiable 3-tier trust system: T1 (Google/GitHub/corporate-backed, 10K+ stars, active maintenance), T2 (established community, 2K+ stars, MIT licensed), T3 (indie/experimental, minimal maintenance signals). Agents select based on the trust tier requirement of the project.
Programmatic trust signal
🔗
4. Co-occurrence Graphs
Mine GitHub production codebases to find which icons appear together in real apps. "settings + user + search + bell + grid" is the sidebar cluster of every major SaaS app. When an agent retrieves one icon, it receives the co-occurrence cluster: "apps using this icon also use these 4 others together."
Pattern propagation
🎨
5. Design System Affinity
An affinity scoring system mapping icon visual characteristics (stroke weight, corner radius, fill style, proportions) to popular component libraries. An agent building with shadcn/ui (2px stroke, sharp corners, neutral) receives Lucide or Tabler icons. Building with Chakra UI (rounded, 1.5px stroke) receives Ionicons or MingCute.
Style compatibility proxy
🔄
6. Icon Morph Pairs
Reviving the dead SVG-Morpheus concept with modern CSS. Premium animated pairs: "play" morphs to "pause," "mic-off" morphs to "mic-on," "thumbs-up" morphs into "check." These express state transitions using single icon slots. The collection defines semantically valid morph pairs, not arbitrary animations.
Motion-native interaction
🚫
7. Negative Knowledge ("Don't Use")
For every intent collection, define icons that are technically findable but contextually wrong. "Don't use a house icon for 'home' in an AI app; use agent.svg because 'home' here means agent base state." Negative knowledge is the most powerful curator signal and is completely absent from every existing library.
Anti-pattern guidance

// 07 — ARCHITECTURE: SOURCE TRUST SYSTEM

How Agents Decide a Source Is Reliable

An agent evaluating an icon source cannot read reviews or sense "this looks legit." It needs quantifiable, verifiable trust signals. The Supericons Trust Tier system makes this explicit and computable.

Tier 1 — Verified Flagship
Core Institutional Libraries
Corporate-backed or community-established with verifiable maintenance, long-term stability, and clear commercial licensing. An agent can cite T1 as "production-safe with no vendor risk."

// 10 — ARCHITECTURE: COLLECTIONS MCP API

The Collections API: What Agents Actually Call

The current Supericons MCP exposes search_icons and get_icon. The curation system requires three new tools that unlock the entire intent-based architecture for agents.

JSONNew MCP Tools Specification
// Tool 1: get_collection_for_intent // Agent asks: "what icons should I use to build X?" { "name": "get_collection_for_intent", "description": "Returns a curated collection of semantically coherent icons for a specific product-building intent. Use this instead of searching individual icons when building a feature area or complete UI section.", "inputSchema": { "intent": "string", // e.g. "AI agent dashboard sidebar" "design_system": "string", // optional: "shadcn", "material", "tailwind" "trust_tier_min": "T1|T2|T3", "format": "string" // "react"|"svelte"|"vue"|"svg" } } // Tool 2: get_icon_manifest // Agent asks: "tell me everything about this icon so I can decide" { "name": "get_icon_manifest", "description": "Returns the full structured manifest for an icon: semantic aliases, trust score, design system affinity, co-occurrence partners, use cases, and contraindications. Use before committing to an icon to validate suitability.", "inputSchema": { "icon_id": "string" // e.g. "supericons:agentic-ai-kit/vector-db" } } // Tool 3: recommend_co_occurring // Agent has one icon, asks what goes with it { "name": "recommend_co_occurring", "description": "Given one icon already chosen, returns the strongly co-occurring icons that typically appear alongside it in production applications. Use to complete an icon set for a feature area when you have already selected a primary icon.", "inputSchema": { "icon_id": "string", "count": "number", // how many co-occurring icons to return "min_strength": "number" // co-occurrence strength threshold 0-1 } }
🤖
How an Agent Now Builds an Icon Set: (1) Call get_collection_for_intent("AI agent dashboard") and receive 12 pre-curated icons with trust scores and React components. (2) Call get_icon_manifest("vector-db") to validate that vector-db matches the shadcn design system detected in package.json. (3) Call recommend_co_occurring("vector-db", 4, 0.8) to get the 4 icons that always appear alongside it. The agent never had to "see" a single icon. It made confident, reasoned choices using structured data.
