Self-Describing Icons

For humans, a picture of a shield means "protection" at a glance. No words needed. What if icons could speak to AI agents the same way? Embed the meaning directly into the file, like a passport carries its owner's identity.

The Core Idea

What If Every Icon Carried Its Own Meaning Inside?

Today, a shield icon is just a bunch of coordinates for AI. It needs a separate database to know what it means. But what if the meaning was baked into the file, like how photos carry their own camera settings?

Why This Is Possible

SVG Is Not Just an Image. It Is a Document.

PNG and JPG are dumb binary blobs. SVG is a structured text document that happens to render as an image. It already supports titles, descriptions, metadata, and custom vocabularies. We just need to use them.

what-svg-already-supports.xml
<svg> <title>Human-readable name</title> <!-- already built in --> <desc>Human-readable description</desc> <!-- already built in --> <metadata>Structured data</metadata> <!-- already built in --> <custom:anything>Your own vocabulary</custom:anything> <!-- supported! --> <path d="..."/> <!-- the visual --> </svg>

No other image format gives us this. SVG is the only format where we can embed rich, structured metadata right next to the visual content, all in one file. This is the foundation for self-describing icons.

Three Approaches

How To Embed Meaning Into an Icon

From practical to revolutionary. Each approach builds on the last.

01
The Passport
Full Metadata Block Inside the SVG

Every Supericons SVG gets a structured "passport" section using a custom vocabulary. When any tool reads the file, it finds everything it needs to know: what the icon means, when to use it, what it pairs with, and how to label it for accessibility.

agent-planning.svg
<svg xmlns:si="https://supericons.dev/ns/v1"> <!-- What humans see --> <title>Planning</title> <desc>An agent is planning its next steps</desc> <!-- What AI reads --> <si:icon id="agent-planning" collection="agent-lifecycle"> <si:purpose>Show that an AI is currently planning</si:purpose> <si:tags>thinking, strategizing, preparing</si:tags> <si:use-when>The agent is planning before executing</si:use-when> <si:dont-use-when>The agent is idle or already done</si:dont-use-when> <si:pairs-with>confidence-badge, authority-marker</si:pairs-with> <si:a11y label="Agent is planning" live="polite"/> </si:icon> <!-- The visual (what renders on screen) --> <path d="M12 2C6.48 2 2 6.48 ..."/> </svg>
badge Like a passport: the icon carries its full identity everywhere it goes
02
The DNA Strand
Compact URI Encoded in One Line

A lighter version. Instead of verbose metadata, embed a single compact line, like a barcode, that encodes the icon's identity. Any tool that knows the format can decode it instantly.

agent-planning.svg (compact)
<svg viewBox="0 0 24 24"> <!-- si://v1/agent-planning/agent-lifecycle/planning/ tags=thinking+strategizing+preparing/ a11y=status:Agent+is+planning:polite --> <path d="M12 2C6.48..."/> </svg>

This URI format is designed to be greppable (search your whole project with one command), parseable (simple URL format), compact (one line), and human-readable (a developer can glance at it and get the idea).

barcode_reader Like a product barcode: tiny, but carries everything about the product
03
The Living Icon
Offline Snapshot + Live Registry Link

The most ambitious version. The icon carries a frozen snapshot of its metadata (works without internet) PLUS a live URL that tools can check for updates (new tags, new pairing rules, new animations).

agent-planning.svg (living)
<si:icon id="agent-planning" version="1.2"> <!-- Works offline (always valid) --> <si:snapshot> <si:purpose>agent-lifecycle</si:purpose> <si:tags>thinking, strategizing</si:tags> </si:snapshot> <!-- Check for updates when online --> <si:live check="https://supericons.dev/api/icons/agent-planning"/> </si:icon>
travel_explore Like a passport with a chip: works at any border, but the chip can be scanned for live updates
What This Makes Possible

Five Things Self-Describing Icons Enable

Once icons carry their own meaning, entirely new capabilities become possible.

01

Icons that introduce themselves

When an agent reads a codebase and finds a Supericons SVG, it does not guess. It reads the icon's own metadata: "I am a planning indicator. I pair with a confidence badge. My accessibility label is 'Agent is planning.'"

02

Meaning travels with the file

Copy a Supericons SVG into any project: its meaning comes along. No account, no server, no API key. The file IS the documentation. Every pasted icon is zero-cost distribution of the Supericons standard.

03

Agents auto-generate accessibility

An agent building a dashboard reads the icon's a11y field and automatically applies the right labels, roles, and aria-live attributes. No hardcoding needed.

04

Automatic icon auditing

A build pipeline scans SVGs in the project: Is this icon used in the wrong context? Are accessibility labels applied? Are versions current? Is the visual language consistent? All answered by reading the files.

05

Each icon becomes a tiny agent

Philosophically, each icon is a tiny autonomous agent. It carries its own context, rules, and identity. It can travel anywhere, be read by any system, and always be understood. The icon does not depend on a server. It IS the knowledge.

How to Build It

Five Steps From Concept to Product

Each step is independently valuable and builds toward the full vision.

1

Define the "passport format." Create the Supericons XML namespace at supericons.dev/ns/v1. Specify the allowed fields: id, collection, purpose, tags, use-when, dont-use-when, pairs-with, a11y. Publish it as an open standard.

2

Build the export pipeline. When a Supericons icon is downloaded, exported via MCP, or shipped in an npm package, the metadata is automatically embedded. The icon never ships "naked." Modify the existing get_icon MCP tool to return SVGs with metadata baked in.

3

Build a tiny reader library. A JavaScript package (under 2KB, no dependencies) that parses metadata from any SVG file. Works as an npm package, a CLI tool for auditing, or inside the MCP server itself.

4

Make the MCP server self-indexing. Instead of a separate icon-index.json, the server reads metadata from its own SVG files at startup. The icons ARE the database. Add a new icon? Just add the metadata inside the SVG. No separate file to keep in sync.

5

Define the compact URI format. The si:// protocol for lightweight embedding: si://v1/agent-planning/agent-lifecycle/planning?tags=thinking+strategizing. Goes into SVG comments for maximum compatibility.

Honest Competitive Analysis

Is This Actually a Moat?

Let's be honest about what competitors could copy and what they cannot.

What is NOT defensible

Embedding metadata in SVG

Any developer can do this in an afternoon. The technical act is trivial.

The namespace schema itself

Open standards are copyable by design. That is the whole point of open standards.

"First to do it"

First-mover advantage lasts months, not years. If the idea is good, others will follow fast.

The tagged icon corpus

If Google decided tomorrow to tag Material Symbols' 3,000+ icons, they could finish in a week with AI. They have more engineers, icons, and distribution.

What COULD be defensible (with the right conditions)

Network effects (agents expect si://)

Strong, if adoption reaches critical mass. Standards are hard to displace once adopted (JSON, Markdown). But you have to get there first.

Telemetry feedback loop

Strong, if MCP usage is high enough. If Supericons is the only system that knows what agents are searching for, it is the only system that can build the right icons proactively. Data moats beat tech moats.

Ecosystem tooling

Medium-strong. Reader library, CI linter, VS Code extension, agent SDK. Switching icon libraries means losing all these tools. Each tool adopted increases switching cost.

Niche ownership

Medium. Too small for Google to care, too specific for Lucide to prioritize, too premium for open-source to replicate profitably. The niche IS the moat.

The real strategy: Own the niche Google will never bother with

Google builds for billions of general users. They will never build a premium pack of 50 "AI governance" icons priced at $29. They will never build a mix-and-match grammar system for compound state indicators. They will never build an MCP tool that returns icons based on intent.

Think of it like Stripe vs PayPal. PayPal is bigger. But Stripe owns the developer payments niche because it is purpose-built for that audience. Supericons can own the "icons for agentic UI" niche the same way.

Self-describing icons is a great product feature, not a moat by itself. The real moat is niche ownership: being the purpose-built, premium, AI-governance icon system. Self-describing metadata, stateful animation, intent-based MCP tools, and composable grammar are all features that reinforce the niche position. The honest formula: niche focus + ecosystem tooling + telemetry feedback loop + speed = defensibility.
