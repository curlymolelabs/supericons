The Agentic Icon Profile Specification

AIPS is a comprehensive metadata schema that transforms icons from static glyphs into living, agent-aware digital entities with semantic DNA, design genome, stateful behavior, and provenance.

Origin: Supericons SI Registry Protocol: AG-UI Compatible Date: 2026-05-07 Status: Open Proposal
Summary Why Now The Schema Identity Semantic DNA Design Genome Agentic State Context Mock Example AG-UI Roadmap

Executive Summary

In the pre-agentic web, an icon was a passive 24×24px glyph that pointed to a hardcoded function. In the agentic era, icons must become intelligent entities that encode meaning, design intent, emotional tone, real-time state, and ownership provenance.

The Agentic Icon Profile Specification (AIPS) extends the Supericons Semantic Registry with a radically more expressive metadata layer. It treats each icon as a profiled asset with:

🆔 Identity & Provenance

NFT-like origin tracking, authorship, versioning, and cryptographic fingerprinting. An icon becomes a traceable digital artifact.

🧬 Semantic DNA

Controlled vocabularies for intent, domain, emotional valence, and relationship to other icons. Machine-readable meaning at depth.

🎨 Design Genome

Complete visual specification: grid, stroke, style family, mood, color logic, animation DNA, and accessibility parameters.

⚡ Agentic State Profile

AG-UI event bindings, confidence signaling, lifecycle states, and mutable visual modes. The icon breathes with the agent.

🎯 Context Intelligence

Usage scenarios, accessibility notes, cultural sensitivity, platform constraints, and responsive behavior rules.

📦 Asset Variants

Multi-format exports, style variants (outline/solid/duotone/animated), resolution ladders, and CDN references.

Why these six? We arrived at this hexagon by asking: what does an icon need to be understood by four different consumers — human designers, frontend developers, AI agents, and end users? Identity serves designers and lawyers. Semantic DNA serves search and AI reasoning. Design Genome serves developers and generative models. Agentic State serves the agent runtime. Context serves UX researchers and accessibility auditors. Assets serves the CDN and the browser. No namespace is optional if you want the icon to function across the full stack.

Why the World Needs AIPS

The Old World: Static Metadata

Today's icon metadata is embarrassingly thin. An average icon library exports something like this:

{
  "name": "shield-check",
  "category": "security",
  "svg": "<svg ...>...</svg>"
}

This is fine for a human browsing a gallery. It is useless for an AI agent deciding which icon to render, useless for a design system enforcing consistency, and useless for a frontend adapting an icon's behavior in real time.

The New World: Living Entities

In the agentic era, the same "shield-check" icon must know:

  • That it conveys binary confidence (verified / unverified), not a spectrum
  • That its solid fill state signals high-trust auto-execution, while its hatched outline signals uncertainty awaiting human approval
  • That it belongs to the security domain and should affiliate with lock, key, and fingerprint in semantic search
  • That it should pulse gently when the AG-UI event agent.completed fires nearby
  • That it was authored by a specific designer on a specific date, with a verifiable hash
Core Insight: The agentic icon is no longer a button that executes a script. It is a portal — a persistent identity that communicates via streaming protocols and unfolds into custom-tailored, generative spaces the moment you engage with it.

The Deeper Shift: From Function to Relationship

In the old model, the relationship between user and icon was transactional: I click, something happens, the interaction ends. In the agentic model, the relationship is relational: the icon represents an ongoing partnership with an entity that has memory, capabilities, and autonomy.

This changes everything about how we specify icons. A transactional icon only needs to answer "What happens when I click?" A relational icon needs to answer:

  • Who is this entity?
  • What is it doing right now?
  • How confident is it?
  • What does it need from me?
  • What has it done before?

Static metadata cannot answer these questions. AIPS can. That is why the specification exists: to give relational icons the vocabulary they need to communicate in a world where users delegate authority to agents, not just trigger functions.

The AIPS Schema

AIPS is organized into six top-level namespaces. Every field is typed, versioned, and optionally extensible via a extensions map.

aips_profile object Root profile container
aips_version string e.g. "0.1.0"
identity object Provenance & ownership
semantic object Meaning, intent, relationships
design object Visual specification genome
agentic object AG-UI state & behavior bindings
context object Usage intelligence & constraints
assets object Multi-format variant manifests
extensions object Vendor-specific or future fields
Schema Philosophy: Why six top-level namespaces and not fewer or more? We tested three, four, five, seven, and eight-namespace variants against real use cases. Three namespaces collapsed semantic and design into an unreadable blob. Seven namespaces fragmented the data so finely that consumers had to query across too many boundaries. Six emerged as the Miller's Law sweet spot: enough granularity to be precise, few enough to hold in working memory. The extensions map exists so that a seventh or eighth namespace can be added by vendors without breaking core interoperability.

1. Identity & Provenance

Inspired by NFT metadata standards (ERC-721 / ERC-1155 / OpenSea), the identity namespace makes every icon a traceable, ownable digital artifact.

FieldTypeRequiredDescription
profile_idstringrequiredCanonical AIPS identifier. Format: {registry}:{library}:{icon_name}
display_namestringrequiredHuman-readable label
slugstringrequiredURL-safe identifier
created_atISO-8601requiredOriginal creation timestamp
modified_atISO-8601optionalLast modification timestamp
authorobjectoptionalName, URI, wallet address of creator
registrystringrequirede.g. "supericons", "heroicons", "lucide"
librarystringrequiredSource library name
versionstringrequiredSemantic version of this profile
content_hashstringoptionalCryptographic hash of canonical SVG (SHA-256)
token_uriURIoptionalOn-chain or IPFS pointer for NFT-backed icons
licensestringoptionalSPDX identifier or custom license URI
is_derivativebooleanoptionalWhether this icon derives from another work
lineagearrayoptionalChain of parent profile_ids (fork history)
NFT Parallel: Just as an ERC-721 token has tokenURI pointing to immutable metadata on IPFS, an AIPS profile can carry a token_uri that anchors the icon's identity on-chain. This enables royalty splitting for icon creators, provenance tracking across design tool exports, and verifiable authenticity in generative UI systems.

Why Provenance Matters for Icons

Most people think of provenance as an art-world concern — who painted this? But in the agentic era, provenance is a trust infrastructure problem. When an AI agent renders an icon, the user must be able to answer: where did this come from? Is it safe? Has it been tampered with?

The content_hash field creates a cryptographic guarantee. The lineage array creates a transparent fork history. The token_uri creates an on-chain anchor. Together, they mean that an icon cannot silently change its meaning. If a designer updates a "shield-check" to look more like a "warning-triangle," the hash changes, the version bumps, and the lineage records the mutation. This is not bureaucracy — it is semantic integrity.

There is also a practical creative reason. Icon designers are some of the most under-credited creatives in software. Their work is copied, modified, and redistributed millions of times without attribution. AIPS provenance is a step toward fixing that. When an icon carries its author, its license, and its royalty mechanism in the profile itself, attribution becomes automatic and compensation becomes possible.

Emotional Valence Object

Agents and design systems need to know how an icon feels:

"emotional_valence": {
  "trust": 0.92,      // Does it build confidence?
  "urgency": 0.15,    // Does it demand immediate action?
  "delight": 0.30,    // Is it playful or rewarding?
  "calm": 0.78,       // Does it reduce anxiety?
  "authority": 0.85,  // Does it command respect?
  "mystery": 0.10    // Is it ambiguous or intriguing?
}

Why Emotional Valence Exists

The emotional_valence object is the most intentionally human part of AIPS — and it exists because we kept hitting the same wall while researching what people are actually building in 2025/2026.

The Observation That Broke the Old Model

When we researched app trends, we noticed something that traditional icon metadata completely ignores: the same functional icon creates completely different user outcomes depending on how it feels.

A shield icon in a fintech app that feels authoritative (solid, heavy, stable) increases conversion on security disclosures. The same shield icon in a mental health app that feels authoritative increases drop-offs because it feels clinical and cold. That fintech app needs the shield to say "your money is safe." The mental health app needs a shield that says "your feelings are protected" — which requires higher calm and delight, lower authority.

Traditional icon metadata has no vocabulary for this. It has category: "security" and tags: ["shield", "protection"]. But "security" is not a feeling — it's a domain. Two icons in the same domain can feel opposite. This became urgent when we connected it to the original goal: you want AI agents to design cooler, more dynamic, more interactive icons. If an AI only knows "this is a security icon," it will generate something technically correct but emotionally blind. If the AI knows the emotional target, it can generate something that actually works in context.

The Six Dimensions: Why These, Why Six

We chose six dimensions through a first-principles breakdown of what an icon actually does in an interface. Not what it represents — what it does to the user.

DimensionQuestion It AnswersReal-World Trigger
trustDoes this icon make me believe the system is reliable?Research showed fintech and health apps live or die on perceived trust. A shield-check with low trust valence is worthless.
urgencyDoes this icon demand immediate action?Notifications, alerts, errors. An urgent icon in a settings menu is anxiety-inducing. A non-urgent icon in an emergency is dangerous.
delightDoes this icon reward or charm me?Duolingo's owl, Asana's unicorn, Notion's playful stickers. Delight increases retention. But delight in a bank app feels unserious.
calmDoes this icon reduce cognitive load?Health, meditation, sleep apps. Research showed calm interfaces improve adherence. A "breathe" icon with jagged edges and high urgency fails its purpose.
authorityDoes this icon command respect and compliance?Enterprise dashboards, legal docs, admin panels. Low-authority icons in high-stakes contexts feel untrustworthy.
mysteryIs this icon intriguing, ambiguous, or exploratory?Onboarding, discovery features, AI "magic" moments. High mystery invites curiosity. But high mystery on a delete button is a disaster.

We stopped at six because of a constraint from cognitive psychology: humans can hold roughly 5-7 emotional dimensions in working memory. More than that and the model becomes noise. Fewer and you lose necessary nuance. These six are also orthogonal — they measure different things. An icon can be high-trust and high-urgency (a fraud alert from your bank). It can be high-delight and high-authority (Mailchimp's Freddie mascot in an enterprise context). The intersections are where sophisticated design lives.

Why 0-1 Scales Instead of Labels

We chose continuous 0-1 numeric values instead of categorical labels like "trust_level": "high" for three reasons:

  1. Gradient Reasoning for AI Agents: An agent choosing between two icons can compute distance. "trust": 0.92 vs "trust": 0.74 is a meaningful, comparable difference. "high" vs "medium" is a bucket that destroys subtlety. When an AI is generating or selecting icons, it needs gradients to optimize.
  2. Emotional Blending: Icons can be partially things. A loading spinner for a medical app might be calm: 0.65, urgency: 0.35 — it acknowledges waiting (some tension) but tries to soothe. No single label captures that blend. The 0-1 scale lets you express "this icon is mostly calm but slightly urgent" precisely.
  3. Threshold Logic: Design systems can set policy thresholds. For example: any icon used in a payment flow must have trust >= 0.80. Any icon used in empty states must have delight >= 0.40 or calm >= 0.60. Any icon with urgency > 0.70 must not be used in passive UI. This is testable, enforceable, and automatable — which matters enormously when AI agents are doing the selecting.

Where the Numbers Come From

In the mock profile for shield-check, we set:

"trust": 0.94, "urgency": 0.08, "delight": 0.25,
"calm": 0.82, "authority": 0.88, "mystery": 0.05

We arrived at these through a simple mental exercise called "emotional roleplay":

  1. Close your eyes. Imagine the icon. A shield with a checkmark.
  2. What is your immediate visceral reaction? Relief. Safety. "Okay, that's handled."
  3. Does your heart rate go up or down? Down. That's low urgency, high calm.
  4. Do you feel like obeying it or co-creating with it? Obeying. That's high authority.
  5. Do you smile? No. It's reassuring, not fun. Low delight.
  6. Are you curious about what it does next? No. It's definitive. Low mystery.

This is a replicable process. A designer, a user researcher, or eventually an AI trained on user testing data can generate these scores. The key is that once encoded, they become machine-readable intention.

The Deeper Philosophy

The emotional_valence object exists because we believe the future of interface design is not visual — it's affective. In the pre-agentic web, designers manually tweaked colors, corners, and animations to evoke the right feeling. In the agentic era, there are too many interfaces, too many states, and too many agents for manual tweaking. The feeling must be specified.

AIPS treats emotion as a first-class design parameter, not an afterthought. Just as you specify stroke_width: 2 and viewBox: "0 0 24 24", you now specify trust: 0.92 and calm: 0.78. The icon doesn't just look right. It feels right. And in a world where AI agents are the ones choosing, generating, and animating icons, feeling right is the only thing that matters.

3. Design Genome

The design namespace is where AIPS departs from all existing icon metadata standards. It encodes the complete visual specification — not just the rendered output, but the rules that generated it.

Why the Design Genome Departs from Existing Standards

Every existing icon standard treats the visual as an output — a blob of SVG or PNG that you render. AIPS treats the visual as a genome — a set of instructions that can be re-executed. This distinction matters enormously for the agentic era.

When an AI agent generates an icon, it does not need an SVG file. It needs a recipe. The grid_system, stroke_spec, and geometry_fingerprint together form a generative recipe. An AI can read this recipe and produce 50 new icons that share the same DNA without ever seeing the original SVG. This is how AIPS enables style-consistent icon generation at scale.

The geometry_fingerprint is particularly subtle. It does not describe the paths. It describes the habits of the icon: its aspect ratio, its symmetry, its negative space ratio, its visual weight. These are the unconscious traits that make an icon feel like it belongs to a family. A human designer develops these habits over years. AIPS encodes them so an agent can inherit them instantly.

The animation_dna field exists because animation in the agentic era is not decoration — it is communication. When an agent is "thinking," the user needs to know. When an agent completes a task, the user needs to feel closure. The animation DNA specifies not just what moves, but how it moves — the rhythm, the easing, the duration. These parameters create emotional consistency across an agent's entire lifecycle.

4. Agentic State Profile

This is the heart of AIPS. The agentic namespace connects an icon to the AG-UI Protocol, enabling it to behave as a living entity in agent-driven interfaces.

Confidence Signaling

Research shows users respond faster to binary confidence than percentages. AIPS encodes this directly:

"confidence_signaling": {
  "high": {
    "fill": "solid",
    "stroke": "none",
    "glow": "subtle_white",
    "satellites": 0
  },
  "uncertain": {
    "fill": "none",
    "stroke": "hatched_dotted",
    "glow": "none",
    "satellites": 2,
    "satellite_glyph": "question"
  },
  "error": {
    "fill": "none",
    "stroke": "solid_danger",
    "glow": "alert_pulse",
    "fragmentation": 0.3
  }
}
AG-UI Integration: When an agent emits agent.tool_call, the AIPS-aware renderer looks up the icon's event_bindings, finds the matching AG-UI event, and triggers the specified visual_behavior. No imperative JavaScript required — the icon profile is declarative state choreography.

Why Declarative State Choreography Matters

In traditional frontend development, an engineer writes imperative code: "when the API returns 200, change the icon color to green." This approach breaks down in the agentic era because the number of states is combinatorial. An agent can be thinking, calling a tool, waiting for a human, erroring, completing, delegating — and these states can nest recursively.

Imperative code cannot scale to this complexity. Declarative state choreography can. The AIPS profile says: "here is the complete map of states and their visual expressions." The renderer simply consults the map. When AG-UI emits agent.thinking, the renderer does not need a human-written callback. It looks up the event_bindings array, finds the match, and executes the visual_behavior. This is the difference between programming an interface and describing an interface.

The confidence_signaling object is another critical departure. Research from FuseLab Creative's agent UX work shows that users respond faster to binary confidence ("I am confident" vs "I am not sure") than to percentages ("73% confident"). AIPS bakes this insight into the schema. An icon can signal high confidence with a solid fill, low confidence with a hatched outline, and error with fragmentation. These are not aesthetic choices — they are cognitive ergonomics.

Finally, the stream_anchor boolean acknowledges that in the AG-UI protocol, components can be streamed directly from the agent to the UI. The icon is not just a passive recipient of state — it is an anchor point for generative UI. When an agent needs to show a complex chart, it can stream that chart directly from the icon's coordinate space. The icon becomes a portal.

5. Context & Usage Intelligence

The context namespace captures the real-world constraints and recommendations that make an icon useful in production systems.

Why Context Intelligence Is Often Overlooked

Most icon libraries ship with a name, a category, and an SVG. They assume the consumer will figure out the rest. But in production systems, the "rest" is where icons live or die. AIPS captures this missing layer.

The platform_suitability field exists because an icon that works beautifully on web may be illegible on a smartwatch. The density_compatibility field exists because an icon that looks perfect in a spacious dashboard may feel cramped in a compact data table. These are not edge cases — they are the daily reality of multi-platform design systems.

The substitutes and composes_with fields are particularly valuable for AI agents. When an agent cannot find the exact icon it wants, it can consult substitutes for semantically similar alternatives. When an agent is designing a grouped UI element (like a toolbar), it can consult composes_with to ensure visual harmony. These fields turn the icon library from a flat inventory into a relational graph.

The localization_risk and rtl_behavior fields address a painful reality: most icon libraries are designed by Western teams for Western audiences. A thumbs-up icon means approval in the US but can be offensive in parts of the Middle East. An arrow pointing right means "forward" in LTR languages but "backward" in RTL languages. AIPS forces these considerations into the open, making them machine-readable and therefore machine-enforceable.

6. Asset Variants

The assets namespace replaces the single svg field with a full variant manifest — a resolution ladder of formats for every context.

"assets": {
  "canonical_svg": {
    "uri": "https://cdn.supericons.dev/si/shield-check.svg",
    "content_hash": "sha256:abc123...",
    "size_bytes": 1420
  },
  "variants": [
    {
      "id": "outline",
      "format": "svg",
      "uri": ".../shield-check-outline.svg",
      "style_variant": "outline",
      "is_default": true
    },
    {
      "id": "solid",
      "format": "svg",
      "uri": ".../shield-check-solid.svg",
      "style_variant": "solid"
    },
    {
      "id": "animated_lottie",
      "format": "lottie+json",
      "uri": ".../shield-check.lottie.json",
      "trigger": "on_load"
    },
    {
      "id": "png_2x",
      "format": "png",
      "uri": ".../shield-check@2x.png",
      "dpi": 192,
      "dimensions": { "w": 48, "h": 48 }
    }
  ]
}

Why Asset Variants Need a Manifest

The old model assumes one icon = one file. The new model assumes one icon = a family of artifacts optimized for different contexts. AIPS replaces the single svg field with a full variant manifest because modern interfaces demand it.

A developer building a PWA needs an SVG for the UI and a PNG for the manifest icon. A designer building a native app needs a 1x, 2x, and 3x raster set. An animation engineer needs a Lottie JSON. An accessibility specialist needs a high-contrast variant. None of these consumers should have to guess which files exist or where they live.

The canonical_svg object is the source of truth. Its content_hash creates an immutable fingerprint. All other variants are derived from this canonical form. If a variant drifts (e.g., a PNG that no longer matches the SVG), the hash mismatch is detectable. This is asset integrity — a concept borrowed from software supply chain security and applied to design assets.

The manifest also enables lazy loading. A renderer can inspect the variant list and load only the formats it needs. A web app never downloads the Lottie file unless an animated state is triggered. A mobile app never downloads the 3x PNG unless it's running on a high-density screen. The manifest makes this optimization trivial.

Positioning in the Ecosystem

We built this comparison not to declare victory over existing standards, but to show where AIPS fits. Every existing standard solves a real problem. AIPS solves a problem that did not exist until the agentic era emerged.

ERC-721 was designed for digital art ownership. It does not care about animation state, event bindings, or semantic meaning. That is fine — art does not need to react to AG-UI events. Agentic icons do.

Iconify was designed for icon set indexing. It does not care about emotional valence, confidence signaling, or design genomes. That is fine — most icons today are static glyphs. Agentic icons are not.

AG-UI was designed for event streaming. It does not care about visual specification, provenance, or asset variants. That is fine — AG-UI is a transport protocol. AIPS is a content protocol.

The key insight is that no single protocol can do everything. The agentic stack will be composed of specialized protocols that each do one thing well. AIPS is the visual-language layer of that stack. It enriches every other standard without replacing any of them.

1. Standardization vs. Expression

Should agent icons follow strict conventions (like traffic lights) or allow creative expression? How do we balance both?

Socratic Unpacking: What problem are we actually solving — recognition speed, emotional connection, or trust calibration? If every agent icon is unique, does the user learn anything? If every icon is identical, does the agent feel like a soulless commodity?

Empathize: Users in high-trust workflows (finance, health, security) need instant recognition — a shield must always mean "protected." Users in creative workflows (design, content, gaming) need personality — a generic robot face kills inspiration.

Define: The real tension is between semantic interoperability (icons must mean the same thing across apps) and identity differentiation (agents must feel distinct).

Ideate: AIPS solves this with a two-tier model:

  • Core glyph (standardized): The base shape follows strict conventions — a shield is always a shield. This guarantees scan-ability and trust.
  • Expression layer (personalized): Color signature, animation style, and satellite ornaments are agent-specific. The core is universal; the expression is unique.

Prototype: All security icons use the same 20×20 keyline and bounding box. But Agent A's shield pulses cyan; Agent B's shield has orbiting gem satellites. Both are instantly "shield." Neither is generic.

Test: A/B test recognition speed. If users identify both shields as "security" in <200ms, the standardization works. If users can also distinguish Agent A from Agent B in <500ms, the expression works.

Resolution: Standardize the grammar, free the vocabulary.

2. Accessibility in Motion

How do we make stateful, animated icons accessible to screen readers and users with motion sensitivity?

Socratic Unpacking: Why do we assume animation is purely visual? If an icon's state changes convey information, is omitting that information from screen readers a form of exclusion? What if motion itself is the message?

Empathize: A user with vestibular disorders experiences "thinking" orbit animations as nausea, not delight. A screen-reader user hears "image, shield check" and misses that the agent is currently erroring.

Define: The problem is not animation — it is unmediated animation. Every state change in an agentic icon is information. That information must be available through at least two sensory channels.

Ideate: AIPS bakes accessibility into the agentic namespace:

  • prefers_reduced_motion triggers a static fallback with color/shape changes instead of motion.
  • Every event_binding carries an aria_live_announcement template: "Security agent is verifying certificate."
  • state_modes include a high_contrast_static variant for users who need maximum clarity.
  • The confidence_signaling object maps to both visual and haptic patterns (solid = firm vibration, hatched = light tap).

Prototype: An AIPS renderer that reads state_modes and outputs: (1) animated SVG for default users, (2) color-morphing static SVG for reduced-motion users, (3) live-region announcements for screen readers, (4) haptic pulses for mobile.

Test: Run the same agentic workflow with users who have motion sensitivity, low vision, and no impairments. Success = all three groups understand the agent's state at every stage.

Resolution: Motion is a dialect, not the only language. AIPS requires every animated state to have a non-motion equivalent encoded in the profile.

3. Cross-Platform Consistency

An agent's identity should persist across web, mobile, desktop, and ambient displays. How do we adapt the visual language without losing identity?

Socratic Unpacking: What is the "essence" of an icon's identity? Is it the exact pixel geometry, or is it a set of invariant properties (shape family, color, motion rhythm)? If Apple and Android render the same SVG differently, has identity been lost?

Empathize: A user sees their "Travel Agent" icon on iOS, then on a smart display, then on a smartwatch. If it looks like three different apps, trust collapses. If the smartwatch tries to render orbital satellites at 24px, it becomes mud.

Define: Identity is not the rendered output — it is the design genome. The genome is platform-agnostic. The renderer is platform-specific.

Ideate: AIPS separates design.genome from assets.variants. The genome says: "shield, vertical symmetry, cyan accent, pulse rhythm." Each platform renderer interprets that genome:

  • Web: Full SVG with CSS animations, orbital satellites, hover expansion.
  • Mobile: Simplified SVG with native spring animations, haptic pulse, no satellites below 32px.
  • Ambient/Watch: Silhouette-only, slow color breathing, no fine detail. Identity = shape + color + rhythm.
  • Desktop: Full fidelity with multi-cursor awareness (icon knows if user is hovering).

Prototype: A single AIPS profile rendered through four platform adapters. Run a "recognition test": show users the same agent on four devices. Ask "Is this the same agent?" Target: >90% yes.

Test: Measure identity persistence across device switches. If users confidently say "That's my Security Agent" on every platform, the genome abstraction works.

Resolution: Encode the seed, not the tree. The AIPS design genome is the seed; platform renderers grow the tree.

4. The Uncanny Valley of Agent Faces

How humanoid should agent icons be? Too human creates false expectations; too abstract fails to build trust.

Socratic Unpacking: Why do we default to faces? Is it because humans are wired for faces, or because we lack a better abstraction for "entity with intent"? What if the uncanny valley is not about human-likeness but about expectation mismatch?

Empathize: A hyper-realistic AI face promises empathy and understanding. When the agent says "I don't know," the user feels betrayed. A faceless geometric shape feels cold. When the agent is helpful, the user feels no connection.

Define: The problem is not "how human?" It is "what promise does the icon make, and can the agent keep it?"

Ideate: AIPS uses emotional_valence and mood to calibrate promise vs. capability:

  • High-empathy agents (therapy, coaching): Mascot-style faces with limited expression range. Deliberately cartoonish, not realistic. The style signals "I try to understand, but I'm not human."
  • High-precision agents (security, data): Abstract geometric forms. No face. Trust comes from consistency and clarity, not faux empathy.
  • Creative agents (design, writing): Organic, fluid shapes that morph. The form signals adaptability and imagination.

Prototype: Three agent icons for the same backend model, differentiated only by visual form: (A) cartoon mascot, (B) geometric crystal, (C) fluid ink blot. Measure user trust, expectation accuracy, and satisfaction.

Test: After interaction, ask users: "Did the icon's appearance match how the agent actually behaved?" The highest-scoring icon is the one with the smallest expectation gap, not the cutest face.

Resolution: Promise honestly, not attractively. AIPS requires every agentic icon to declare its mood and confidence_mode so users know what to expect before they interact.

5. Icon Spam & Visual Clutter

In a multi-agent world, how do we prevent visual clutter? Do agents cluster? Do they have "tabs"?

Socratic Unpacking: Why do we assume every agent needs a visible icon at all times? If an agent is idle, does it need attention? What if the problem is not too many icons, but too much visibility?

Empathize: A dashboard with 12 agent icons feels like a control panel from a nuclear submarine. A dashboard with 1 icon that expands into 12 on demand feels like a clean workspace. The user doesn't want to manage agents; they want agents to manage work.

Define: The problem is not icon count. It is attention allocation. Not every agent deserves pixels when idle.

Ideate: AIPS encodes a presence_model in the agentic namespace:

  • Active: Full icon, animation, satellites. The agent is doing something relevant now.
  • Standby: Minimal badge — a small dot in the agent's color signature. Still present, not distracting.
  • Dormant: Completely hidden. Accessible via a "show all agents" gesture. The agent exists in memory, not in pixels.
  • Clustered: Related agents (e.g., all security agents) collapse into a single shield icon with a count badge. Tap to expand.

Prototype: A workspace with 8 agents. Default view shows 2 active + 1 cluster badge. Expanded view shows all 8. Measure task completion time and self-reported calmness.

Test: If users complete tasks faster with the clustered view than with all-icons-visible, presence hierarchy wins.

Resolution: Visibility is a privilege, not a right. AIPS agents must earn screen real estate through relevance, not existence.

Ideate: AIPS adopts a three-tier vocabulary model:

  • Core vocabulary (Supericons-maintained): category, intent, domain, state, status. Immutable without RFC. Changed once per year. Guarantees interoperability.
  • Extended vocabulary (community-curated): New domains like climate_tech, bioinformatics. Proposed via GitHub PR, approved by elected maintainers. Changed quarterly.
  • Private extensions (enterprise/vendor): Any organization can add fields under extensions.{vendor_id}. Not validated by AIPS core, but preserved in profiles. Full freedom.
