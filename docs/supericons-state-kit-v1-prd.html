01

Problem

What developers actually experience

Every piece of software needs to communicate state to users: something is loading, something succeeded, something went wrong, something is waiting for approval. These are not edge cases. They are the most common interactive moments in any app.

Despite this, most teams ship one of three inadequate solutions:

  • A static spinner from an icon library, repurposed for every state regardless of meaning
  • A CSS animation hacked together for this one case and never reused
  • A Lottie or Rive file that adds 200KB+ to the bundle and requires a separate player

The result is inconsistency within products and across them. A "loading" icon looks different from the "retrying" state which looks identical to "syncing." Users cannot read the visual signal. Developers waste time on work that should be solved once.

Why existing solutions do not solve this

SolutionProblem
FontAwesome / Lucide / PhosphorStatic files only. No state, no animation, no semantic guidance.
Lottie / RiveHeavy runtime dependency. Complex toolchain. Requires design software expertise. Not developer-friendly.
CSS spinnersOne-off. No semantic consistency. No accessibility metadata. No guidance on when to use each.
AI-generated SVGsVisually inconsistent. No semantic layer. No motion behavior. No accessibility.
Building in-houseExpensive, slow, and not a core competency for most teams.

What is missing

There is no product that provides animated state icons with:

  • Semantic meaning — what this icon communicates, not just what it looks like
  • Behavioral guidance — when to use it, when not to, what it implies to users
  • Accessibility built in — ARIA labels, reduced-motion behavior, contrast requirements met
  • Zero runtime dependency — pure SVG, no player required
  • Agent-readable metadata — so AI coding tools can find and use the right icon

State Kit v1 fills this gap.

Core insight

AI can generate a loading spinner. It cannot generate the right spinner for a high-risk financial transaction with correct ARIA labeling, reduced-motion fallback, and a semantic profile that tells an agent when to use it versus a different icon. That specificity is the product.

03

Scope

In scope for v1

  • 50 animated SVG icons covering the core software state vocabulary
  • One semantic profile per icon (structured JSON): state, risk, confidence, motion behavior, ARIA label, use-when, avoid-when, example contexts
  • Static SVG fallback for every animated icon
  • Reduced-motion variant for every animated icon
  • Three delivery formats: raw SVG, React component, Web Component
  • One MCP search tool: find an icon by intent or state description
  • Demo page with live state toggles, copy-paste snippets, profile viewer
  • One paid purchase path (Lemon Squeezy or Gumroad)

Out of scope for v1

See Section 12 for full rationale. Summary:

  • Parametric customization props (Phase 2)
  • AI-assisted generation (Phase 3 / Forge)
  • Registry or token namespacing (Phase 4)
  • Visual editor / Studio (Phase 4)
  • Native mobile (iOS / Android) renderers
  • Canvas or WebGL output
  • Team collaboration features

Design constraint

All 50 icons must belong to the same visual family. Line weight, corner radius, grid size, stroke caps, and color palette are defined once and applied consistently. Inconsistency within the set destroys the product's core value proposition.

05

Icon profile spec

Every icon ships with a machine-readable JSON profile. This is not documentation — it is data that the MCP tool, future parametric system, and agent workflows consume directly. Write it carefully. These profiles are the semantic layer that justifies the product's existence.

Profile schema

loading-ring.json
{
  "id": "loading-ring",
  "name": "Loading Ring",
  "version": "1.0.0",
  // What this icon semantically represents
  "semantic": {
    "base_object": "process",
    "state": "loading",
    "risk_level": "none",
    "confidence": "high",
    "urgency": "neutral",
    "reversible": true
  },
  // What to put in aria-label — exact text, not instructions
  "accessibility": {
    "aria_label": "Loading",
    "aria_live": "polite",
    "role": "status",
    "reduce_motion": "static-ring"
  },
  // Motion characteristics — for future parametric control
  "motion": {
    "type": "loop",
    "duration_ms": 1200,
    "easing": "ease-in-out",
    "communicates": "continuous indeterminate progress"
  },
  // Guidance — this is the semantic layer humans and agents read
  "guidance": {
    "use_when": [
      "A process has started and completion time is unknown",
      "The system is working and the user should wait",
      "No specific action is required from the user"
    ],
    "avoid_when": [
      "You know the completion percentage — use loading-bar instead",
      "The wait is for a human action — use pending-approval instead",
      "The process has failed and is retrying — use retrying instead"
    ],
    "example_contexts": [
      "Form submission processing",
      "File upload in progress",
      "API request pending",
      "Dashboard data loading"
    ],
    "not_for": [
      "AI agent activity — use ai-thinking or ai-working instead",
      "Dangerous or irreversible operations — use a warning state"
    ]
  },
  // Files shipped with this icon
  "files": {
    "animated_svg": "loading-ring.svg",
    "static_svg": "loading-ring-static.svg",
    "reduced_motion_svg": "loading-ring-reduced.svg",
    "react": "LoadingRing.tsx",
    "web_component": "loading-ring-wc.js"
  }
}

Field definitions

FieldTypeRequiredNotes
semantic.statestring enumYesloading, success, error, warning, blocked, retrying, idle, pending, processing, ai-active, risk-low, risk-medium, risk-high
semantic.risk_levelstring enumYesnone, low, medium, high, critical
semantic.confidencestring enumYeshigh, medium, low, uncertain — describes what this icon implies about system confidence, not design quality
semantic.reversiblebooleanYesTrue if the state can naturally resolve. False for terminal states like error-critical.
accessibility.aria_labelstringYesExact text. Not instructions. Tested with a screen reader before shipping.
accessibility.aria_livestring enumYesoff, polite, assertive. Most states are polite. Critical errors may be assertive.
accessibility.reduce_motionstringYesID of the reduced-motion variant for this icon.
motion.communicatesstringYesOne sentence. What the animation communicates, not describes. This is read by agents.
guidance.use_whenstring[]Yes2–4 items. Specific conditions, not general truisms.
guidance.avoid_whenstring[]Yes2–4 items. Each item names the correct alternative icon.
guidance.example_contextsstring[]Yes2–6 real app scenarios. Specific, not generic.
Quality bar

A profile passes review only when: a developer reading it for the first time knows exactly which icon to use and which to avoid, and an AI agent reading it can construct a correct recommendation without hallucinating. If the guidance is vague enough to apply to any icon, it is not done yet.

06

Delivery formats

What gets shipped

Every icon is delivered in three formats. All three ship with every purchase. There is no upsell for a specific format.

Format 1 — Raw SVG

Three files per icon: animated, static fallback, reduced-motion. Animation is implemented using CSS @keyframes embedded directly in the SVG. No JavaScript. No external dependencies. Inline in HTML or referenced as an <img> tag or CSS background-image.

Constraint: Animated SVGs used as <img> or CSS background-image do not animate in most browsers — only inline SVG animates reliably. Document this limitation clearly in the README and demo page. Do not hide it.

Reduced-motion variant uses @media (prefers-reduced-motion: reduce) inside the SVG to replace motion with a static or very subtly pulsing version. No JavaScript required.

Format 2 — React component

TypeScript, no runtime dependencies. Props in v1:

// LoadingRing.tsx
interface LoadingRingProps {
  size?: number;          // px, default 24
  color?: string;         // CSS color, default currentColor
  label?: string;         // aria-label override
  className?: string;
}

The component wraps inline SVG. It respects prefers-reduced-motion automatically via a useReducedMotion hook, swapping to the static variant without any prop required from the developer.

The component includes role="status", aria-label, and aria-live per the profile spec. Developers can override the label for context-specific strings like "Saving your changes…"

Format 3 — Web Component

Custom element registered as <si-icon name="loading-ring">. Framework-agnostic. Works in plain HTML, Vue, Angular, Svelte, and any other environment.

<!-- Plain HTML usage -->
<script type="module" src="/si-icons.js"></script>

<si-icon
  name="loading-ring"
  size="24"
  label="Saving your changes"
></si-icon>

Reduced-motion is handled automatically inside the component. No developer action required.

07

Demo page

The demo page is a product, not a marketing page. Most developers who encounter State Kit will make their purchase decision here. If it does not demonstrate value clearly within 30 seconds, the product fails regardless of how good the icons are.

Page requirements

  • Live icon grid. All 50 icons visible and animated. Visitors see the product immediately on load, without scrolling or clicking.
  • State toggle. Click any icon to see its states: animated, static, reduced-motion. One click, instant visual feedback.
  • Profile panel. Selecting an icon shows the semantic profile inline: state, risk level, use-when, avoid-when, example contexts, ARIA label. This demonstrates the depth behind the visuals.
  • Copy snippet. Each format (SVG, React, Web Component) has a one-click copy button. The code shown is production-ready — copy, paste, works.
  • Reduced-motion toggle. A global toggle that simulates prefers-reduced-motion: reduce, so visitors can see what users with that preference experience.
  • Search. Type "error" or "AI" or "blocked" and the grid filters to matching icons. Uses the profile data, not just icon names.
  • One CTA. "Buy State Kit — $X" visible at all times. No modal, no email capture gate, no friction before the purchase link.

Performance constraints

  • Page must load in under 2 seconds on a standard connection
  • Icons load lazily as the user scrolls — do not load all 50 SVGs at once
  • No analytics or tracking scripts that block render
  • Passes Lighthouse accessibility audit score of 95+

What the demo page is not

  • Not a blog post or explainer. The icons demonstrate themselves.
  • Not a feature list. Show; do not tell.
  • Not a Figma embed or screenshot. Real, live SVGs only.
08

MCP tool

One tool at launch. Not five tools, not a complex workflow — one reliable tool that solves the specific problem an AI coding agent faces: "I need to show the user that something is loading / failed / blocked. What icon should I use and how do I use it?"

Tool: search_state_icons

Tool definition

Name: search_state_icons

Description: Find the right Supericons State Kit icon for a software state or interaction. Describe what the user is experiencing or what the system is doing. Returns the icon name, SVG, React usage, semantic profile, and accessibility label.

// Input schema
{
  "query": string,         // natural language description of the state
  "context"?: string,      // optional: app type, user type, risk level hint
  "format"?: string        // "svg" | "react" | "web-component", default "react"
}

// Output
{
  "icon_id": string,
  "icon_name": string,
  "match_reason": string,  // one sentence: why this icon, not another
  "aria_label": string,
  "usage_snippet": string, // paste-ready code in the requested format
  "profile": object,       // full semantic profile JSON
  "alternatives": array   // up to 2 other candidates with brief reason each
}

Behavior requirements

  • Deterministic. The same query returns the same icon. Agents need to trust that the tool will not return different icons for the same state on different calls.
  • Grounded. Results come only from the actual 50-icon set. The tool never invents an icon ID or returns an icon that does not exist.
  • Match reason is always provided. An agent should never have to guess why this icon was selected. The match_reason is one clear sentence that distinguishes this icon from its alternatives.
  • Alternatives are conservative. Return 0–2 alternatives, not 8. More choices create more confusion. If the best match is clear, say so and return no alternatives.
  • Accessibility is pre-filled. The usage snippet includes aria-label populated from the profile. The developer does not have to think about it unless they want to override it for context.

Example call

// Agent query
search_state_icons({
  query: "The payment is being processed and the user should wait",
  context: "fintech app, high-value transaction",
  format: "react"
})

// Response
{
  icon_id: "loading-ring",
  icon_name: "Loading Ring",
  match_reason: "Indeterminate wait with no user action needed matches payment processing; loading-bar would imply known progress",
  aria_label: "Processing payment",
  usage_snippet: "<LoadingRing label='Processing payment' size={24} />",
  profile: { ... },
  alternatives: [
    {
      icon_id: "processing",
      reason: "More technical feel; appropriate if the UI is developer-facing"
    }
  ]
}
Do not ship

Do not ship a tool that generates new SVGs, modifies icons, or creates parametric variants. v1 is search and retrieval only. Generation belongs in Phase 3 (Forge). Trying to do both in v1 dilutes both.

Build timeline

Timeline assumes one primary builder. Adjust if there are additional contributors. Do not compress weeks 1–4 — the design foundation created in that period determines the quality of everything that follows.

Weeks 1–2
Foundation — visual system and first five icons
Define the visual system: grid (24×24), stroke weight, corner radius, color palette, animation timing conventions. Design and implement all five P0 loading/progress icons (loading-ring, loading-dots, loading-bar, uploading, downloading). Write their profiles. Get the quality bar right before proceeding. These five icons set the standard for the remaining 45.
Weeks 3–4
Core states — all P0 icons complete
Complete remaining P0 icons: syncing, success, error, error-critical, warning, blocked, paused, pending-approval, retrying, ai-thinking, ai-working. All with animated SVG, static fallback, reduced-motion variant, and profile. Accessibility review on all P0 icons — screen reader test, contrast check, motion review.
Weeks 5–6
P1 icons and React component build
Design and implement all P1 icons. Build the React component wrapper including useReducedMotion hook, TypeScript props, aria-label handling. Write barrel export. Test React components in a real Next.js project. Fix any SVG animation issues discovered in component context.
Weeks 7–8
P2 icons, Web Component, and MCP tool
Design and implement all P2 icons. Build the Web Component (si-icon custom element). Build the MCP search tool — index all profiles, implement semantic search, write the tool definition, test with at least five realistic agent query scenarios. Verify tool output is copy-paste correct.
Weeks 9–10
Demo page build and QA
Build the demo page: live icon grid, state toggle, profile panel, copy snippets, reduced-motion toggle, search. Lighthouse audit — target 95+ accessibility, 90+ performance. Cross-browser test (Chrome, Firefox, Safari, Edge). Test on mobile. Run demo page with 3–5 developers who have not seen it before and observe where they are confused.
Weeks 11–12
Packaging, payment, and launch
Write README, CHANGELOG, license text. Assemble zip file. Set up Lemon Squeezy product page with three tiers. Soft launch to a small list (25–50 people) for final feedback. Fix anything critical. Public launch: post on X, submit to relevant newsletters (Bytes, React Newsletter, TLDR), post on HN Show HN if the response is strong enough.

Risks

RiskLikelihoodMitigation
Visual inconsistency across 50 icons High Define and document the visual system in week 1. Review every new icon against the first five before proceeding. Do not rush weeks 1–2.
SVG animation compatibility issues Medium Test every P0 icon in Chrome, Firefox, and Safari before proceeding to P1. Animated SVG has well-known cross-browser edge cases — find them early.
Profiles are too generic to be useful Medium Use the quality bar: a profile passes only when the avoid_when items each name a specific alternative icon. Generic guidance is a rewrite, not a pass.
Demo page does not convert Medium Test with 3–5 developers before launch. Watch where they get confused. If they cannot find the copy button in under 10 seconds, redesign that part.
MCP tool returns hallucinated icon IDs Low with discipline The tool must search against the actual profiles index, not generate freeform. Test with edge-case queries ("what icon for quantum-encrypted upload?") and verify the output references a real icon ID.
Timeline slips due to icon count Medium P0 icons are launch-blockers. P1 and P2 are not. If week 8 arrives and P2 icons are incomplete, launch with 35–40 icons and ship the rest as a free update. Shipping on time with a strong set beats a perfect set shipped late.
No one buys it Low-medium The product exists. Learn from the failure mode: is it discovery, demo, price, or the product itself? Each has a different fix. Do not iterate blindly — identify the failure before changing something.
