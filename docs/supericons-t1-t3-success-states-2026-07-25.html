T1

Traffic classification and the organic denominator

Purpose: make the search stream trustworthy enough that anything can be built on top of it. Scope shrank after the audit. Rows are not unclassified today: classifyMcpTraffic already stamps every event and already treats the signed controlled-run marker as authoritative. What is missing is a distinction inside live traffic, where probes and organic use share one bucket, and a reported organic denominator. Step 0 is a single query to find out whether the rest is even needed.

You will know it worked when

  • Step 0 first: the existing traffic_class distribution is known. If signed labelling already catches most non-organic traffic, skip the build and go to T2.
  • Organic searches, organic identities, and unknown share are stated together, never one without the others.
  • The rule re-runs unattended as code, not a hand-curated list.
  • It has been validated against a session known to be genuine, confirming agent retries survive.

Trap: over-filtering. Agents legitimately retry and rephrase, so repetition alone is not proof of a bot. Test the rule against sessions you recognize as real before trusting it. Deleting genuine agent traffic would quietly destroy your best signal.

Revised after audit. Identity count alone classifies nothing. The phrase above showed 6 fingerprints but also 4 IPs, 5 user agents, four client families and 3 countries inside four hours; it was the client and country spread that indicated testing, not the count. Since fingerprints are network configurations rather than people, require at least two independent signals before calling anything a probe. Scope also shrank: classifyMcpTraffic already exists and already treats the signed controlled-run marker as authoritative, so the work is probe detection plus an organic denominator, not a new classifier. You will know it worked when

  • Face validity passes. The top 50 reads like icons people actually need. Anything strange up there means T1 was incomplete.
  • The order is stable day to day. Thrashing at your volume means the window is too short or the evidence too thin.
  • A stale score is now loud, not silent. The April failure hid for three months because nothing on screen showed freshness.
  • You can answer "popular on web or popular with agents" for any icon.

Decide before you code: 162 scored rows against 21,000+ icons means coverage under 1%, and it will stay sparse. So this is not "rank All Icons by popularity," it is "rank the top N by evidence, then something deliberate for the other 19,800." Choose that tail behavior and label it, or you have invented an ordering, which is a VC-6 problem.

T3 ✓

Resolve what estimated reach counts

Closed 2026-07-25, independently audited against production. Purpose was to know which decisions the numbers can support. Success was never a flattering answer, and it did not deliver one: it confirmed the mechanism, removed a claim that had already spread into three documents, and surfaced a concentration risk nobody had measured.

Today · a number with no definition
Estimated reach
632
632 what? People? Sessions? Agent restarts?

The local session ID is a per-process UUID hashed with the date, so one person restarting their agent four times looks like four searchers. Whether hosted behaves the same way is unverified. Every conclusion drawn from this number is provisional until it is.

Answered 2026-07-25 · from source
Estimated unique clients
632
Hosted identity hashes IP, user agent, client family and month bucket. Stable within a calendar month.
Returning clients · within month
already built
Clients active on 2+ days. Exists in the metrics lib and admin API, simply not on the Overview.

Not sessions. Only local npm, about 1% of traffic, rotates per process. What remains is display work: surface returning clients, state the definition on the card, and prefer within-month windows since the 30-day preset crosses a month boundary and double-counts anyone active either side of it.

Why this small task mattered, though not in the way expected. The session-versus-people question resolved cleanly in favour of month-stable identity. But an independent production audit then removed a claim that had already spread into three documents, and surfaced a different number that matters far more.

✕ Withdrawn · the "4% conversion rate"

27 all-time accounts over 632 recent identities is a ratio between two populations across two different spans, not a measured conversion. Only 2 identities are account-linked, so nothing connects a searcher to a registration.

What the audit actually settled

  • Identity is month-stable, not session-scoped. 100% of hosted rows carried the hash; 153 identities recurred across days.
  • A fingerprint is not a person. Twelve user agents produced 629 identities, so it is closer to an IP count. Read it as clients or networks.
  • Returning clients is not display-only work. The V2 Overview API does not expose it, and the old endpoint's value includes untrusted local activity.
  • Conversion cannot be measured until accounts link to searches, which is rung 1 itself.

Correct status: identity definition confirmed, hosted identities month-stable, person-level reach and registration conversion remain unverified. The strategic weight moved from the funnel to the concentration: one directory supplies 96.5% of identities, and that channel also has the weakest registration path, since a user inside ChatGPT has no browser session to sign up in.
