# PRD: Admin Dashboard Refinement (Icon Intelligence v2)

- Status: Draft for owner review
- Date: 2026-07-14
- Owner: Curly Mole Labs
- Supersedes in part: `docs/supericons-admin-user-intelligence-dashboard-prd-2026-07-04.md` (the Query Explorer sections; the ledger and privacy sections remain valid)

## 1. Background

Traffic is growing slowly through referrals from Google and from OpenAI ecosystem clients. The admin needs two things the current dashboard cannot answer reliably:

1. Where users come from (acquisition source and channel).
2. Whether their searches meet their needs (search outcome quality).

A telemetry audit on 2026-07-14, run against the live production endpoints and a 7-day Query Explorer export (4,327 query rows, 2,000 exported), found that the recording layer is accurate but the presented numbers are distorted. Any dashboard refinement must fix the data before repainting the UI.

Audit findings that motivate this PRD (all verified against code and live endpoints):

- About 70 percent of query rows are internal recommend_icons slot-variant searches (machine-built queries combining slot text with the full task text), not queries any user or agent issued directly.
- About 15 percent of rows are get_icon ID lookups displayed as if they were search queries (two pseudo-query rows per lookup).
- One hosted MCP search is counted as two attempts because the same call is logged to both `mcp_usage_events` and `search_request_audit` and the aggregator does not dedupe between them.
- `result_count` is capped by the caller's requested `limit`. Tool guidance recommends limits of 1 to 3, so the "Low results" issue badge mostly flags successful searches.
- 250 of 252 material-filtered query rows are zero results due to a product defect: Material Symbols entries carry no SVG, and the MCP server drops SVG-less rows. A separate transient phosphor incident (2026-07-12 to 07-13) produced zero results for common queries; the engine is healthy for phosphor as of 07-14.
- After removing the above noise, roughly 43 genuine content-gap queries remain in the week. That signal is the core value of the dashboard and it is currently buried.
- Identity fields are structurally empty: no request in the window carried an API key, web search runs client-side without identity, and country is always null because the geo code reads CDN headers that the Railway host never sets.
- No referrer or UTM capture exists anywhere in the web codebase, so acquisition source is not recorded at all today.

## 2. Goals

- G1: The admin can see, on one screen, how much real usage happened, where it came from, and whether searches succeeded.
- G2: Every zero-result or low-result signal shown by default is actionable (a real gap in content, aliases, or engine behavior), not an artifact.
- G3: Acquisition channels are measured: Google organic and other web referrers, OpenAI ecosystem clients (ChatGPT connector), Claude clients, other MCP clients, and direct web.
- G4: Search outcome quality is measured with honest definitions that survive the known distortions.
- G5: Country-level geography works for hosted MCP traffic.
- G6: Registered users become visible where they actually act (web), and the anonymous MCP population is reported honestly as anonymous cohorts.
- G7: Full raw-data drill-down remains available for arbitrary investigation.

## 3. Non-goals

- No per-user behavioral profiles or cross-site tracking. Aggregate and hashed identifiers only, consistent with the existing privacy posture (hashed IPs, no raw IP storage).
- No city-level or finer geography. Country only.
- No OAuth login for the hosted MCP endpoint in this phase (recorded as a later option; see Open Questions).
- No changes to the public search engine ranking behavior (covered by the Search v2 workstream).
- No paid analytics vendor. Existing stack (Supabase, Netlify, Railway, optional Umami) only.

## 4. Users

Single persona: the owner-admin. Uses the dashboard a few times per week to (a) spot problems, (b) triage content gaps into registry work, (c) understand growth. Sessions are short; the default view must answer the important questions without configuration.

## 5. Definitions

These definitions are normative for every metric on the dashboard.

- Direct query: a search issued by a user or agent through `search_icons`, or the exact task string of a `recommend_icons` call, or a web grid search. Identified by `query_origin = 'agent_query'` (see FR-2).
- Machine variant: an internal search generated by recommend_icons slot expansion (`query_origin = 'recommend_variant'`).
- Icon lookup: a get_icon resolution search (`query_origin = 'icon_lookup'`).
- Attempt: one deduplicated search event. When both a usage-ledger row and an audit row exist for the same `dedupe_key`, they count as one attempt.
- True zero: an attempt with `result_count = 0` on a direct query, excluding attempts that failed due to a known engine defect (tracked defects get their own flag; see FR-5).
- Capped result: an attempt where `result_count` equals the caller's requested limit. Capped results are successes, never "low results".
- Low result: an attempt with `0 < result_count < min(requested_limit, 3)`. Requires the requested limit to be logged (FR-4).
- Session: existing `session_hash` (web) or `mcp-session-id` hash (hosted MCP).
- Client family: existing `client_family` classification (chatgpt, claude, opencode, unknown, and future values).
- Acquisition channel: one of `web_search` (Google and other engines, from referrer), `web_referral` (other sites), `web_direct`, `mcp_chatgpt`, `mcp_claude`, `mcp_other`, `unknown`.

## 6. Functional requirements

### Phase 1: data integrity (prerequisite for everything else)

- FR-1 Material Symbols SVGs. Generate real SVG assets for the Material Symbols library into the icon index and hosted catalog so material-filtered MCP searches return icons. Acceptance: hosted search with `library=material, mode=strict` returns results with non-null SVG for the top 50 common queries; the MCP server returns them; new material zero-result rows drop to near zero.
  - Interim step if asset generation is deferred: remove `material` from `list_libraries` and tool descriptions so agents stop requesting a library that cannot be served, and make the MCP server surface a clear "library unavailable" note instead of silently returning zero.
- FR-2 Query origin tagging. Add `query_origin` (`agent_query`, `recommend_variant`, `icon_lookup`) to `search_request_audit` and `mcp_usage_events`. Writers: the MCP server sets it per call site (top-level tool call vs recommend inner search vs get_icon resolution). The admin API groups and filters on it. Default explorer and all headline metrics use `agent_query` only. Acceptance: the 7-day query list under default filters contains no slot-plus-task machine strings and no icon-ID pseudo-queries.
- FR-3 Attempt dedupe. The admin API deduplicates evidence rows sharing a `dedupe_key` (and links via the existing `search_request_audit_id` column where present) before computing attempts, zero counts, and averages. Acceptance: a single hosted search_icons call produces exactly one attempt in the workbench row.
- FR-4 Requested limit logging. Log `requested_limit` on audit and ledger rows. Redefine the Low results badge per Section 5. Acceptance: an attempt with `limit=3, result_count=3` is classified successful, not low.
- FR-5 Known-defect flagging. Maintain a small server-side list of known engine defects (library, date range, defect id). Attempts matching an active defect are labeled `engine_defect` and excluded from True zero, shown instead in Engine health. Acceptance: material zeros stop inflating the gap worklist while the defect is open, and reappear if the defect list entry is removed.

### Phase 2: acquisition attribution

- FR-6 Web referrer capture. The web app records `document.referrer` (origin only, not full URL) and UTM parameters (`utm_source`, `utm_medium`, `utm_campaign`) once per session, stored on evidence rows or a small `web_session_context` table keyed by `session_hash`. Referrer origins are classified into `web_search` (google., bing., duckduckgo., etc.), `web_referral`, `web_direct`. No full referrer paths, no personal data.
- FR-7 MCP client attribution. Acquisition channel for MCP traffic derives from `client_family`: `mcp_chatgpt`, `mcp_claude`, `mcp_other`. Surface `mcp_server_version` distribution alongside, since client behavior changes by version.
- FR-8 MCP-to-web bridge measurement. MCP responses already embed preview URLs carrying `?preview=mcp`. The web app logs a `preview_visit` evidence event when it loads with this parameter (session-scoped, aggregate only). This measures how often agent sessions convert into human web visits, which is the referral loop from OpenAI ecosystem usage back to the site.
- FR-9 Country for hosted MCP. Resolve country in the Railway server from the client IP using a local GeoIP database (for example MaxMind GeoLite2 country), before hashing the IP. Store only the two-letter country code, consistent with the existing `country_code` column and privacy posture. Fallback remains the existing CDN header chain, so fronting the service with Cloudflare later requires no code change. Acceptance: at least 90 percent of new hosted MCP events carry a country code.
- FR-10 Registered-user visibility on web. Pass the authenticated user id (or a stable hash of it) into web evidence logging so registered activity is countable. Aggregate display only ("N registered users active this week"), no per-user drill-down in this phase.

### Phase 3: dashboard restructure

Four views. The existing Query Explorer remains, demoted to the Explorer tab.

- FR-11 Overview (default view, one screen). Content, in order:
  1. Attempts per day (deduped, direct queries only), 14-day sparkline with 7-day-over-7-day delta.
  2. Distinct clients per day (distinct `ip_hash` plus `anonymous_client_hash` union) with the same delta.
  3. Acquisition channel split (Section 5 taxonomy) as a single stacked bar with counts.
  4. Outcome summary for direct queries: success rate, true-zero rate, low-result rate, clarification rate, error rate. One row of five numbers.
  5. "Needs attention" list: top 10 open items from the Gaps worklist plus any active engine-defect alert.
  Everything on this view links into the corresponding deeper view with filters pre-applied.
- FR-12 Gaps worklist. A triage queue of true-zero and genuine low-result direct queries, grouped by normalized concept, ordered by attempt volume. Each row: query, attempts, distinct clients, libraries requested, first and last seen, and the existing triage actions (Needs alias, Needs icon, Resolved, Ignore) as primary buttons. Resolved and ignored rows leave the queue. Acceptance: the queue length after Phase 1 fixes is measured in dozens, not thousands, and every row is a real gap on inspection.
- FR-13 Engine health. Per-library true-zero rate over time (line per library, the defect detector), latency p50 and p95 from `latency_ms`, error and clarification rates, active known defects (FR-5) with start dates, and a "failed icon lookups" list from `icon_lookup` attempts with zero results (agents guessing icon IDs that do not exist; useful naming feedback). Acceptance: replaying the July 12-13 phosphor incident data on this view shows an obvious spike within the day.
- FR-14 Explorer (advanced). The current Query Explorer with all existing filters plus new ones: `query_origin` (default `agent_query`), acquisition channel, country, client family, known-defect flag. Exports (CSV, JSON, agent pack) gain the same fields. Nothing is removed.
- FR-15 Display honesty cleanup. Remove permanently-empty placeholders from row rendering for MCP traffic: purpose filter, source domain, replaced count, and country (until FR-9 ships) move into the detail drawer and render only when data exists. Labels never imply missing data that cannot exist for that channel.

### Phase 4: identity depth (later, gated on demand)

- FR-16 API key visibility nudge: tool descriptions and docs mention that registered users can attach their API key for higher tiers; the dashboard shows keyed vs anonymous MCP share. Expect low adoption; this is instrumentation, not a growth lever.
- FR-17 (Deferred, decision required) OAuth on the hosted MCP endpoint for real user attribution in ChatGPT and Claude connectors.

## 7. Metrics and success criteria

Dashboard-level acceptance after Phases 1 to 3:

- The Overview answers "how much, from where, did it work" with zero configuration, using only direct queries.
- Attempt counts drop by roughly half for search_icons rows (dedupe) and the default query list shrinks by roughly 85 percent (origin tagging), matching the audit's predicted noise share.
- True-zero rate becomes a stable KPI: after the material fix it should sit well under 10 percent of direct-query attempts; sustained spikes indicate either a new defect (Engine health) or a real content gap wave (Gaps worklist).
- Acquisition: 100 percent of MCP attempts and at least 80 percent of new web sessions carry a channel classification; hosted MCP country coverage at least 90 percent.
- Gap triage throughput: every item in the worklist can be dispositioned, and dispositions persist (existing review store).

## 8. Data model changes

| Change | Where | Notes |
|---|---|---|
| `query_origin` text | `search_request_audit`, `mcp_usage_events` | default `agent_query` for backfill; index on it |
| `requested_limit` int | same tables | nullable |
| `known_defect_id` text | computed at read time from defect list; optionally materialized | avoids rewriting history when defects are declared later |
| `referrer_origin`, `utm_source`, `utm_medium`, `utm_campaign` | new `web_session_context` table keyed by `session_hash`, or columns on `icon_evidence` | origin only, no paths |
| `preview_visit` signal | `icon_evidence` (`signal_type`) | logged when web app loads with `preview=mcp` |
| `user_ref` (hashed user id) | `icon_evidence` | web only, aggregate reporting |
| GeoIP db + lookup | Railway MCP server | country only, before IP hashing |
| Defect registry | small JSON or table (`engine_defects`) | id, library, date range, description |

Migration policy: all columns nullable and additive; the admin API already has column-fallback handling for older schemas and this pattern continues.

## 9. Rollout and verification

1. Phase 1 ships behind no flag (data-only). Verify: replay the 7-day export through the new aggregation and confirm the predicted collapses (attempts halve on search rows; default list drops to real queries; material rows leave the gap queue once the defect entry exists).
2. Phase 2 web changes ship with a console-visible debug flag; verify referrer classification against a manual visit from a Google search result, a direct visit, and an MCP preview link.
3. GeoIP verified by comparing a sample of new events against known request origins.
4. Phase 3 UI ships view by view: Overview first, then Gaps, then Engine health, Explorer filter additions last.
5. Each phase ends with a fresh agent-pack export reviewed against the acceptance criteria above.

## 10. Open questions

1. Material Symbols: generate SVGs (larger one-time pipeline work, permanent fix) or de-advertise the library short-term and schedule the pipeline? The PRD assumes de-advertise now, SVG pipeline as its own scheduled task.
2. Umami: the 2026-07-04 PRD proposed importing Umami aggregates for web geography and page analytics. Keep as optional enrichment or drop from scope? This PRD does not depend on it.
3. OAuth for hosted MCP (FR-17): revisit when there is a commercial reason to attribute individual connector users (for example, MCP-side Pro entitlements).
4. Retention: current queue queries scan full history for the "all" window; growing traffic may need a rollup table (daily aggregates) around the 100k-events mark. Out of scope here but flagged.

## 11. Out-of-scope reminders recorded during the audit

- The phosphor 2026-07-12/13 zero-result incident resolved without intervention but had no detection; FR-13 is the systematic answer.
- The recommend_icons slot-query construction (slot text concatenated with full task text) produces poor inner queries and is a search-quality issue in its own right, tracked separately from this dashboard PRD.
