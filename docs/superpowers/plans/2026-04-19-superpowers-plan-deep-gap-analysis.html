Deep Audit

Superpowers Plan Deep Gap Analysis

Multi-lens analysis: Systems Thinking, Technical Architecture, Competitive Strategy, Operational Reality, Business Model. April 19, 2026.

Purpose

Second-pass audit using different analytical lenses from the first feasibility audit. Every finding is backed by codebase evidence gathered in this session. Only genuine gaps are reported.

Update note: the companion plan docs were updated after this audit to add the verified fixes. Keep this file as the record of what was missing before those updates.

Lens 1: Systems Thinking

Systems

Gap 1: Premium Manifest Already Has 60% of v1 Fields

public/packs/manifest.json (4,927 lines) is a top-level object keyed by 8 collection slugs and already contains per-icon purpose, tags, and category for all 400 premium icons. The existing data satisfies about 60% of the minimum v1 work right away.

Impact: The premium normalization is likely a 2-4 hour scripted transform, not a multi-day effort. This means Phase 1 can deliver faster than the plans suggest.

Systems

Gap 2: Taxonomy Seed vs. Registry Reconciliation Is Unplanned

lib/icon-taxonomy-seed.js has 150 hardcoded icon IDs across 3 categories. This is a manually curated list with no connection to any semantic pipeline. The registry also assigns categories through metadata fields.

When the registry exists, what happens to the seed? Three possibilities exist (legacy input, replaced by projections, or co-existing indefinitely), but none are discussed in any document.

Impact: Medium-High. The purpose-chip experiment and the registry will compete for category ownership.

Systems

Gap 3: 12-Tool MCP Has No Per-Tool Registry Integration Map

MCP registers exactly 12 tools: search_icons, get_icon, list_libraries, list_motion_presets, get_motion_recipe, export_motion_css, export_animated_svg, animate_icon, inspect_converter_options, inspect_converter_input, convert_svg_to_png, convert_png_to_svg.

The plans treat MCP as a monolithic consumer. But each tool has different data needs. No per-tool integration mapping exists.

Impact: Medium. "Integrate registry with MCP" is an unbounded task without this.

Lens 2: Technical Architecture

Architecture

Gap 4: Three Conflicting ID Formats With No Resolution Rule

Registry spec example: si:agent-planning (prefix:name).
MCP tools: {id: "heart", library: "lucide"} (two fields).
Taxonomy seed: material:smart_toy (library:name composite).

The spec defines icon_id as "globally unique" but does not specify the generation rule or collision resolution.

Impact: High. Every downstream consumer that indexes by ID will need migration if the format changes.

Fix: Define one shared ID format: {source_library}:{source_name} for aggregated, si:{name} for native. Document the rule, not just examples.

Architecture

Gap 5: No Transition Plan from build-icons.js to Registry Projections

scripts/build-icons.js currently reads from npm-installed icon packages to produce icon-index.json. Registry projections would produce the same artifact from different source data.

Two different data sources producing the same output artifact with no cutover plan. If both run, the product ships contradictory data.

Impact: High. This is a dependency inversion that needs a concrete transition plan.

Architecture

Gap 6: Hardcoded "20,000" Appears 133+ Times; Blast Radius Not Inventoried

Found in: index.html (8 instances in title, meta, hero, search, stats), store.js (6+ instances in pricing/docs HTML), docs-pages.js (5+ instances), main.js (2 instances), mcp/index.js (1 instance), mcp/SKILL.md (1 instance), plus 25+ instances across strategy docs.
Meanwhile, root package.json says "60K+" and MCP comment says "3 tools" (actually 12).

A naive search-and-replace is unsafe because some instances are deliberate marketing copy while others should show exact counts.

Fix: Create a complete inventory classifying each as "marketing" / "product truth" / "technical" before applying fixes.

Lens 3: Competitive Strategy

Strategy

Gap 7: No Competitive Benchmarking of SI Metadata vs. Existing Systems

Simple Icons ships structured JSON with title, slug, hex, source, guidelines, license. Iconify.design ships a unified JSON API across 150+ sets with category filters. The plans claim differentiation through "semantic purpose and confidence" but never benchmark against these.

Impact: Low. Unique SI fields (avoid_when, anti_pairs, confidence_score, motion_family) are genuinely novel. But the differentiation case would be stronger if stated explicitly.

Lens 4: Operational Reality

Operations

Gap 8: Review Infrastructure Is Fully Missing

The rollout roadmap defines confidence routing (auto-accept, batch review, deeper review) and cadence (nightly, weekly, monthly). The spec defines review_state values. But there is no review UI, no review queue, no review CLI, and no review workflow in the codebase.

Building a review queue requires: a list view of pending records, side-by-side comparison, approve/reject actions, and confidence filtering. This is a product feature, not a script.

Impact: High. Without review tooling, the "confidence-aware review workflow" is unreachable. Hidden dependency that blocks the continuous factory model.

Fix: Add a task: "Build a minimal review interface (CLI or admin page) for viewing, approving, and rejecting batched semantic records."

Operations

Gap 9: Visual Inspection Pilot Has No Tool Selection or Cost Estimate

The pilot is likely cheap enough that cost should not block it, and a local open-source lane may be close to zero extra cost if the hardware already exists. But the plans never state even a simple budget guardrail or execution lane.

Impact: Low. Stating the cost removes ambiguity.

Lens 5: Business Model

Business

Gap 10: No Revenue Hypothesis Connecting Registry Quality to Business Metrics

None of the four documents draw a line from registry improvements to conversion, retention, or pricing. If better metadata increases free-to-paid conversion or reduces churn, that should be stated as a hypothesis to validate.

Impact: Low for a solo founder. Higher if seeking investment.

Actionable Recommendations

Must-fix before building (3 items)

  1. Lock the ID format. Define {source_library}:{source_name} for aggregated, si:{name} for native. Add as a normative rule.
  2. Map the build pipeline transition. Document how build-icons.js will yield to registry projections. Define the cutover.
  3. Reconcile taxonomy seed with registry. Decide: seed is deprecated when registry categories exist, or seed is a legacy layer. Do not leave both alive without a plan.

Should-fix before Phase 2 (2 items)

  1. Build a minimal review interface. Even a CLI is sufficient. Without it, confidence routing is unexecutable.
  2. Inventory all hardcoded count strings. Classify each as marketing / product truth / technical with intended source.

Nice-to-have (2 items)

  1. Acknowledge premium manifest richness in the implementation plan.
  2. State a simple visual pilot budget and the planned hosted and local lanes.
