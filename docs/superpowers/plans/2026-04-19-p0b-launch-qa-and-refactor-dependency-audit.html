P0-B Audit

Launch QA passed. The next risk is refactor safety.

This review checked the launch-facing flows after the P0 facts and title fixes, then mapped where the frontend is most tightly connected so we can refactor without breaking the app.

Checked packs, collection detail, pricing, MCP docs, search placeholder, empty state
Good news No new blocking browser regressions showed up in the tested flows.
Main risk The shell, store routes, and CSS are still tightly tied together.

What was tested

  • The premium collections page
  • A premium collection preview and detail page
  • The pricing page
  • The main docs page and the MCP tools docs page
  • The search box placeholder in icons mode and docs mode
  • A no-results search state

What passed

  • The premium collections page kept the correct heading. The old overwrite bug is gone.
  • Opening a collection preview switched the heading to the correct collection title.
  • The pricing page showed the shared fact labels we moved to the new facts layer.
  • The MCP tools docs showed the real tool count: 12 tools, with 3 free tools.
  • The search box still changes correctly between Search docs and Search 20,000+ icons....
  • A nonsense search showed a clean no-results message instead of a broken screen.
  • No browser console errors appeared during the checked flows.

What still needs attention

Route links are not fully consistent

Some store pages like packs and pricing open correctly from a ?view= link, but the browser address later gets cleaned back to /. Docs pages keep their ?view= address.

That means deep links work on entry, but copy-and-share behavior is less clear after the page loads.

Static landing copy still lives outside the facts layer

The app shell and docs now read shared product facts in the areas we changed, but the landing page title, meta tags, and some hero copy in index.html are still hand-written.

The build still warns about bundle size

The app builds successfully, but the JavaScript bundle is still large. That is not a launch blocker for this slice, but it is a sign that the code needs cleaner boundaries.

Where the code is tightly connected

main.js

This file owns the shared app shell: the icon grid, panel, compare drawer, header search, and many event listeners.

The main risk is that other parts of the app reuse the same shell pieces, so changes here can ripple across many screens.

store.js

This file is both the route controller and the host for many features: packs, pricing, docs, dashboard, API keys, Motion Lab, Converter, and more.

It reaches directly into shell-owned parts like the main grid, panel, and title areas. That is the highest refactor risk in the app right now.

style.css

This stylesheet covers almost every product surface in one file. It also contains repeated selector groups, especially around pricing and docs.

That makes visual changes slower and raises the chance of accidental overrides.

Plain-English takeaway: the problem is not just that the files are big. The problem is that the app shell, the store screens, and the CSS all depend on each other in quiet ways.

Safe order for the next refactor

  1. Create one shared shell contract for the title, grid, panel, preview, and search box.
  2. Move route rules into one route registry so URL behavior is easier to reason about.
  3. Extract the docs rendering first because it is lower risk than billing or premium access.
  4. Extract pricing next because it is visible, valuable, and already has repeated CSS blocks.
  5. Extract the premium collections surface only after the shell contract is stable.
  6. Leave Motion Lab and Converter for later because they carry more tool-specific state.

Best next step

The next implementation slice should be a small shell-and-routing cleanup, not a full registry build yet.

  • Decide whether packs, pricing, dashboard, and downloads should keep their ?view= URL.
  • Add a shared shell adapter so store code stops touching raw shell DOM directly.
  • Use that cleaner boundary to extract the docs feature first.

No user-only manual test is required before that work starts. If we choose to change route persistence next, that is the first place where a quick manual check in your app browser will be useful.
