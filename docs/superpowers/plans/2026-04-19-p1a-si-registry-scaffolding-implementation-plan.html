P1-A Implementation Plan

Build the first real SI Registry foundation

This phase creates the first real home for Supericons meaning. The goal is not to tag every icon yet. The goal is to create the main shared record system, lock the ID rules, add validation, and prove that Supericons can build useful registry outputs without breaking the live product.

Simple rule: make the registry real first, then scale tagging later.

P1-A

This plan. Build the registry skeleton in code without cutting over the live app yet.

What This Phase Must Achieve

  • Define the main shared record for one icon.
  • Lock one ID rule that every tool and file can follow.
  • Make the public, protected, and private data split explicit.
  • Create a small set of real sample records.
  • Build preview outputs from those records.
  • Fail fast if records are missing required fields or use bad values.
  • Keep the current live icon files untouched while this new system is being proven.

What This Phase Does Not Do

  • It does not tag all 21,264 free icons yet.
  • It does not replace the live icon index yet.
  • It does not replace the browse taxonomy yet.
  • It does not add review UI yet.
  • It does not force search, MCP, or the website to read from the registry yet.

This is a build-the-foundation phase, not a full rollout phase.

Main Rules Locked By This Plan

  • The registry lives in the repo as the main official source for future icon meaning.
  • The registry is hybrid from the start. Some parts can become public, some must stay protected, and some stay private only.
  • Live product files stay as they are for now until a later cutover.
  • IDs are locked early:
    • aggregated icons use {source_library}:{source_name}
    • SI-native icons use si:{name}
  • The first record set stays intentionally small.
  • The difference between source identity, visual depiction, SI recommendation, evidence, confidence, and review must remain visible.

Hybrid Visibility Model

This phase should not leave the public/private split vague. It should define it in code and in the source files.

1. Public open records

These are safe to expose for free and open icons. They can feed future public lookup pages, public data files, and other trust-building surfaces.

2. Protected premium records

These use the same overall record shape, but they should not become public outputs by default. This protects premium value while still letting the registry stay consistent.

3. Private operating data

This includes things like telemetry, ranking logic, internal review notes, editorial scores, and model traces. This data should never leak into public outputs by default.

4. Generated outputs

The build step should be able to create different outputs for different audiences:

  • a public-safe output
  • an internal preview output
  • later, other product-specific outputs if needed

5. Simple control fields

The first registry records should include small control fields such as:

  • access_tier to say what level of visibility the record belongs to
  • projection_policy to say which outputs it is allowed to flow into

The big idea is simple: one record system, but not one visibility level for everything.

Implementation Steps

1. Create the registry folder and starter records

Make one clean home for the new system inside data/si-registry/. Add a short README, a registry manifest, a visibility-rules file, a controlled-values file, and two tiny record sets: one premium sample and one free pilot sample.

2. Lock the hybrid visibility model in code

Add a small helper that loads the visibility rules and checks that every sample record says whether it is public, protected, or private-facing. Make sure the build can create a public-safe output without leaking protected or private data.

3. Lock the ID rules in code

Add a small helper that builds and validates registry IDs. This should be strict, because every future file and tool will rely on it.

4. Lock the record shape in code

Add a clear helper that checks which fields are required now, which ones are optional, which values must come from an approved list, and which control fields decide visibility.

5. Build preview outputs

Create a build script that reads the sample records, validates them, and writes preview files. These preview files should include an internal preview and a public-safe preview so we can inspect the split clearly without changing the live site.

6. Add verification that fails fast

The verification script should stop the build if there are duplicate IDs, missing required fields, bad controlled values, bad visibility settings, leaked protected data, or broken output files.

7. Keep the no-cutover rule explicit

Make it clear in the README and plan notes that this phase does not replace:

  • public/icon-index.json
  • mcp/public/icon-index.json
  • public/icon-taxonomy.json
  • public/packs/manifest.json

8. Make the first examples teach the model clearly

Use one free sample that is public-facing and one premium sample that is protected by default. If useful, add a note showing what kinds of internal operating data should stay private later.

Later, if package scripts are added:

npm run build:si-registry

What Success Looks Like

  • The registry folder exists and is understandable.
  • The public, protected, and private split is defined clearly.
  • ID rules are locked in code.
  • The record shape is checked in code.
  • A small premium and free pilot record set exists.
  • Preview outputs build successfully.
  • The public-safe preview does not leak protected or private data.
  • Bad registry data causes verification to fail.
  • The live app still uses the current production files for now.

After that, the next phase is premium normalization and a small free import, not a giant full-corpus tagging jump.
