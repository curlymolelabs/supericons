Screenshot Quality Workflow Map

This page shows the exact step-by-step process for the new screenshot quality workflow in plain language. The goal is simple: let the programs handle the repeatable work, and let the agent only do the human part, which is writing a better visual description in the depicts field. There is one main workflow and four common run modes built on top of it.

Programs choose the batch Agent writes depicts only Programs check quality and promotion

Run Modes

Run mode What it is for Prompt file
Status and capture Check counts and render screenshots if needed. docs/superpowers/workflows/screenshot-quality-prompts/01-status-and-capture.md
Review only Select a batch, write depicts, finalize, audit, and stop for QA. docs/superpowers/workflows/screenshot-quality-prompts/02-review-only.md
Promotion only Take an approved final-records file and promote it live. docs/superpowers/workflows/screenshot-quality-prompts/03-promotion-only.md
Full cycle Run review, audit, approval, promotion, and final verification in one flow. docs/superpowers/workflows/screenshot-quality-prompts/04-full-cycle.md

Who Does What

The programs do this

  • Check what is already live, pending, or untouched.
  • Pick the next icons in order.
  • Build the agent packet with screenshot paths.
  • Turn depicts-only output into full public records.
  • Run rule checks before promotion.
  • Promote approved records into the live public registry.

The agent does this

  • Open the screenshots for each selected icon.
  • Write one shared visual description for line and fill styles.
  • Return only icon_id and depicts.
  • Pause for review before anything is promoted live.

Exact Workflow

Step 1

Check the current state

First, ask the program what is already finished, what is reviewed but not live yet, and what still needs work.

npm run screenshot-quality -- status --library mingcute --json
Program used: scripts/screenshot-quality-workflow.mjs with the status command.
Safe places to change: --library. This lets the same workflow run on another library later.
Step 2

Capture screenshots if they are missing

If the screenshot folder is not ready yet, use the screenshot program to render the icon PNG files from the source icon catalog.

npm run capture:icon-screenshots -- --library mingcute
Program used: scripts/capture-icon-screenshots.mjs. It reads the screenshot mapping file and writes PNG files into the output screenshot folder.
Safe places to change: --library, --limit, --width, and --height. Use --dry-run if you only want to preview what will be rendered.
Step 3

Let the program choose the next batch

Do not let the agent decide which icons come next. The program picks the next untouched icons in source order and writes a packet file for the agent.

npm run screenshot-quality -- select --library mingcute --size 100 --batch-id mingcute-screenshot-batch-034
Output: data/si-registry/manual-redo/mingcute-screenshot-batch-034-packet.json
Program used: scripts/screenshot-quality-workflow.mjs with the select command.
Safe places to change: --size for icons per batch and --batch-id for the batch name. This is the main batch size control point.
Step 4

Give the packet to the agent

The agent reads the packet, looks at the screenshot files, and writes a depicts-only JSON file. The agent should not edit the other public fields.

Input file: data/si-registry/manual-redo/mingcute-screenshot-batch-034-packet.json
Expected agent output: data/si-registry/manual-redo/mingcute-screenshot-batch-034-agent-depicts.json
Human rule: one semantic record per icon. Line and fill are usually one shared depicts, not two separate ones.
Step 5

Turn depicts-only output into full final records

After the agent returns the depicts-only file, the program merges those new descriptions back into the live public record shape while keeping the other public fields unchanged.

npm run screenshot-quality -- finalize-review --library mingcute --batch-id mingcute-screenshot-batch-034 --agent-output data/si-registry/manual-redo/mingcute-screenshot-batch-034-agent-depicts.json
Output: data/si-registry/manual-redo/mingcute-screenshot-batch-034-final-records.json
Program used: scripts/screenshot-quality-workflow.mjs with the finalize-review command.
Step 6

Run the automatic quality check

The program checks for common mistakes such as copy-paste wording, missing visible details like an off slash, or generic phrases that are too vague.

npm run screenshot-quality -- audit-quality --final-records data/si-registry/manual-redo/mingcute-screenshot-batch-034-final-records.json
Program used: scripts/screenshot-quality-workflow.mjs with the audit-quality command.
This step should pass before promotion. If it fails, fix the batch, do not push it live.
Step 7

Review the final records before promotion

Pause here and inspect the final records JSON. This is the human review stop. Nothing should be promoted live before this check.

Review file: data/si-registry/manual-redo/mingcute-screenshot-batch-034-final-records.json
Human checkpoint: this is where we check whether the new descriptions are actually good, not just rule-clean.
Step 8

Promote only after approval

Once the batch is approved, the promotion command merges the new public fields into the approved records file, rebuilds the live registry, and confirms that the live registry now matches the final records.

npm run screenshot-quality -- promote --library mingcute --final-records data/si-registry/manual-redo/mingcute-screenshot-batch-034-final-records.json
Program used: scripts/screenshot-quality-workflow.mjs with the promote command.
Avoid --allow-quality-issues unless there is a very clear manual exception and we consciously accept the risk.
Step 9

Verify the workflow stays clean

After promotion, run the repo-level workflow checker. This confirms there are no broken final-record files, no bad overlap state, and no missing required record structure.

npm run verify:screenshot-quality-workflow
Program used: scripts/verify-screenshot-quality-workflow.mjs.

What We Can Safely Change

Thing we may change Where to change it What it affects
Library name --library Chooses which screenshot folder, mapping, and approved records file the programs use.
Icons per batch --size on the select command Controls how many icons the agent processes in one review cycle.
Batch name --batch-id Changes the packet and final-record file names for that run.
Screenshot preview count --limit on screenshot capture Lets us test a small number of renders before running a full library capture.
Screenshot size --width and --height Changes the PNG output size used by the renderer.
Whether to only preview work --dry-run Shows what the program would do without writing the final files.
